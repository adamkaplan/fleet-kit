## Cause (clause 1)

The preflight runs every test file of cloud/launcher/tests and cloud/worker/tests one at a time on the branch and again on a clean copy of the base. In a pod this did not finish within 300 seconds, so the pre-push command ended with "could not run the preflight". The documentation states this cause first, with the measured times from a real run.

## Open choices (one recommendation each)

- (a) How the quick mode selects checks. Recommendation: a shared helper in bin/ imported by both commands, with one test of it. Cost: a small refactor of the selection code of bin/cloud-prepush (#1297), so #1297 must be in first; reuse by copy would drift.
- (b) What "the named scans" are. Recommendation: the same literal list as cloud-prepush (SCAN_TESTS), with a test that both lists are equal. Cost: one more test; a change to the list is made in one place, and the test fails if only one is edited.
- (c) The default of the pre-push command. Recommendation: quick by default, CLOUD_PREPUSH_PREFLIGHT=full for the whole check. Cost: the default pre-push no longer runs every test; the full mode stays one variable away and the CI remains the full check.
- (d) Build order. It can only start after #1209 and #1297 are in the integration branch. Cost: the work waits on them; planning and tests of the helper may be drafted meanwhile but not pushed ahead.

## Out of scope

Changing which tests exist, the CI, the per-file timeouts, the allow list of timeouts, the base selection, or the other bounds of bin/cloud-prepush.
