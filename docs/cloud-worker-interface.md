# Cloud worker interface (slices A, B, C)

The contract between the three parts of cloud workers (ask #323, plan rev 2.1), so they can be built in parallel.
**A** is the worker image. **B** is the launcher, the reaper and the end hook. **C** is switchboard support for a
remote worker. Names here are the shared vocabulary; a change to one is a change to this file first.
Items marked **OPEN** are not decided.

## 1. Launcher commands (slice B)

One program, `cloud-worker <command>`; every command takes `--json` (one JSON object on stdout; progress goes to stderr).
`<worker>` matches the switchboard's agent name rule. Nothing local changes: local launch, reattach and retire stay as they are.

| Command | Inputs | Output (stdout JSON) | Effect |
|---|---|---|---|
| `create <worker>` | `--repo OWNER/NAME`, `--branch B`, `--idle 10m` (default), `--hard 2h` (default), `--shape S\|M`, `--stack` | the endpoint record (section 3) plus `runtime_id` | starts one pod from the image with the environment of section 2; returns only once the worker answers |
| `stop <worker>` | `--reason TEXT`; `--run-id NONCE`; `--record-dir DIR`; `--no-record` | `{worker, runtime_id, pushed, wip_branch, skipped, record}` | first writes the run record (below), then runs the end hook (section 5), then rewrites the record's `run.json` once with the hook's result (`end_hook`: `ran`, `pushed`, `wip_branch`, `skipped`, `note`, `error`), then deletes the pod and its scratch volume. `record` is the record directory, `""` when none could be made |
| `extend <worker>` | `--hard +1h` or an ISO time; `--idle 30m` | the new deadlines | moves the deadlines; never past `--max-hard` (default 8h, **OPEN**: value); the pod itself carries a cluster-side floor at that cap (section 6) |
| `delete <worker>` | `--force` | `{worker, runtime_id, deleted}` | removes the pod and its leftovers without the end hook; refused unless the hook ran or `--force` is given; used by the reaper after a kept pod is resolved |
| `report <worker>` | none (`--json` for an object) | one line: the worker's report | read only; `kubectl exec <pod> -- head -c ... /home/worker/report`, scrubbed, one line, at most 2000 characters; exit `3` with `no report yet` when the file is missing or empty. Nothing of the switchboard is in the pod |
| `prune-records` | `--days N` (default `$CW_RECORD_KEEP_DAYS`, else `30`); `--record-dir DIR` | `{root, days, removed}` | removes this tool's per-run record directories older than N days; nothing else (see the run record) |
| `status [<worker>]` | none | one record per worker: `{worker, runtime_id, phase, idle_since, deadlines, cost_estimate_usd}` | read only |

Exit codes: `0` done; `1` the end hook could not push, **the pod is kept** (stop only); `2` bad usage or unknown worker;
`3` the cloud refused (quota, identity, cap); `4` timed out waiting for the worker; `5` the spend cap is reached
(create only; the cap is `CW_CLOUD_SPEND_CAP_USD`, default USD 25 when unset or empty, and an invalid value or an unreadable cost refuses the create); `6` refused: `delete` before the end hook ran without `--force`, or `extend` past `--max-hard`. Every other failure is `1` with a one-line reason on stderr.

The launcher reaches the cluster with an explicit `--context` taken from `CW_KUBE_CONTEXT` (and `--kubeconfig` from `CW_KUBECONFIG` when set). With no context configured it refuses every command (exit `2`) and makes no call; it never uses the active context. A `create` that is interrupted or fails removes the Secret and pod it made, audits `create.interrupted` or `create.failed`, and names anything that could not be removed.
Instead of a context the launcher can log in as the namespace service account: set `CW_CLOUD_SERVER` (an https URL whose host is a DNS name, `https://NAME[:PORT]`) and `CW_CLOUD_TOKEN_FILE` (and optionally `CW_CLOUD_CA_FILE`, a path). It then generates a minimal `0600` kubeconfig in a private temporary directory, removed at exit, whose only credential is the token file's path (never a token value, never `--token`), and every call uses it. The two logins are never mixed: with both a context or kubeconfig and the token settings it refuses (exit `2`). A missing, empty or unreadable token file exits `3` with `token unavailable` and makes no call; no other credential is tried. The account is `cw-operator` in `cloud/k8s/operator-rbac.yaml`: namespaced to the workers namespace, only pods, their logs, exec and port-forward, and secrets, with no wildcard and nothing cluster-wide.

`create --stack` (opt-in; off by default, and a create without it builds the same pod as before) asks for a pod that can run a nested Docker stack on the Sysbox runtime. The pod then has `runtimeClassName: sysbox-runc`, `hostUsers: false` (its own user namespace), `nodeSelector: {sysbox-install: "yes"}` (the node POOL label; the half-ready `sysbox-runtime=running` is never used), `runAsNonRoot` (the image's `worker`, uid 1000) and the annotation `cw/stack: "true"`. It has NO privileged flag, NO hostPath volume, NO Docker socket mount, NO host network, PID or IPC, no added capability and no service-account token. The hard limits stay: shape `S` (2 CPU, 4 GiB) is the smallest existing shape that holds the stack lane's measured peak (1.0 to 1.35 GiB, 1 to 2 CPUs) with the worker and the daemon on top; `M` also works; the pod is never unlimited. Its container security context is the one constant `STACK_SECURITY_CONTEXT` (`allowPrivilegeEscalation: true` because `sudo start-dockerd` needs it, every capability dropped, none added): it was live-probed with the cluster default only, and the smallest set that lets a non-root worker start the daemon is decided by the next live run, one variation at a time. One table, `FORBIDDEN_POD_FIELDS`, lists what no pod may have (hostPath, docker.sock, privileged, hostNetwork, hostPID, hostIPC, `hostUsers: true`, an added `SYS_ADMIN` or `ALL` in any spelling (case and a `CAP_` prefix do not matter), a service-account token) plus two stack-only allow-list rows: every container's (init and ephemeral too) security context must EQUAL `STACK_SECURITY_CONTEXT`, so any other added capability fails until the constant and its test change together, and the runtime class, node selector, `hostUsers: false`, annotation and pod-level user and seccomp must equal what the builder sets; `create` refuses a pod spec that has any member, stack or not.
**The fresh-node race.** A pod created as a fresh node scales up can fail with `FailedCreatePodSandBox` and "RuntimeClass handler sysbox-runc does not support user namespaces: the handler sysbox-runc is not known", because the node's containerd is configured by the installer about 30 to 60 seconds after the pod is scheduled. For `--stack` the launcher reads the pod's events while it waits and, on exactly that message (matched on the handler-not-known text, and only for the events of this pod object, by its uid), deletes the POD and creates it again with the same run id and nonce (exclusive create; a pod whose run id is not this call's is left whole). At most 3 attempts; a race seen after the 4-minute window (`STACK_ATTEMPTS`, `STACK_RACE_WINDOW_SECONDS`) is not retried (the window is checked when a race event is seen; each attempt still waits up to `--wait`). Without `--run-id` the ownership check is vacuous (the first create is still exclusive); the run-task driver always sends one. The password Secret and the per-run Secret are made once, before the first attempt, and are never touched by a retry (the pod refers to them by name). **A pod that vanishes while pending** (it was seen by a get, and a later get says not found: the node's container runtime restarted and took the Pending pod object with it) is recreated the same way: same run id and nonce, the secrets untouched, the same attempt cap and window, and an audit line whose reason is `attempt N of 3: pod vanished`. Before it recreates, the launcher checks that this call's own Secrets (the password Secret and, when made, the per-run Secret) are still there: when one is gone the pod was removed from outside (an operator `stop`, the reaper, someone else), and the create fails with a message that says so, without recreating (the cleanup then runs as for any failed create). The check also runs right after a recreate and before the create reports the pod ready, so a stop whose Secret deletes land before the last of these checks is refused. This narrows the race and does not close it: a stop that deletes the pod and whose Secret deletes land after the last check can leave a recreated pod, reported ready, whose Secrets are gone (the pod and Secret deletes are not one step); if that pod never starts, the create's own wait ends and its cleanup deletes it, and if it started and was reported ready the stop has finished, so the only later catch is the reaper at `--hard` (or the idle limit). A Secret get that errors (not "not found") fails the create. A Secret that carries another run's id counts as gone. A pod that was never seen, and any other failure, is not retried. The window bounds the COUNT of attempts, not the wall time: it is checked after each attempt ends, so the worst case is 3 attempts of up to `--wait` plus the 150 s delete wait each. After the window or the attempts the create fails (exit `3`) with a message that names the race (or the vanish), and the cleanup removes the pod and both Secrets as for any failed create. Each attempt writes one audit line, action `create-attempt`, whose reason starts `attempt N of 3:` (`ok: false` for an attempt that hit the race or failed, `ok: true` with `ready` for the one that worked), followed by the create's own line. A create without `--stack` makes no events call and no attempt line.
`create` may also take `--pull-secret NAME` (an existing image-pull Secret, referenced by `imagePullSecrets`) and, repeated, `--run-secret-fd NAME=N`: each value is read once from the inherited descriptor `N` and sent to `kubectl` on stdin into one per-run Secret `<pod>-run`, mounted read-only at `/run/cw/NAME` (mode `0400`), never an argument, environment variable or spec field. That Secret is deleted at `stop` (when the pod is deleted), at `delete`, and when a `create` fails or is interrupted; it is kept when `stop` keeps the pod because the end hook could not push. A pod that is already `Failed` or `Succeeded` is deleted by `stop` with its Secrets (no hook can run, so its unpushed work is discarded, and stderr says so); a pod kept for a failed push (`cw/kept`) is never deleted this way. At most 8 run secrets, each at most 1 MiB, else exit `2`. With a run secret supplied, `CW_TOKEN_ENDPOINT` is optional.
Settings that decide which repositories a worker may serve (read from the environment; exit `2` with `refused: <repo> is not on the cloud allow-list`, before anything is created):

| Setting | Meaning |
|---|---|
| `CW_ALLOWED_REPOS` | comma-separated `OWNER/NAME` allow-list, exact and case-insensitive, no wildcard; unset, empty or a malformed entry refuses every repository; read from the environment of whoever runs the launcher or driver (the operator exports it), so a mistake-guard for the operator, not a boundary: the stops are the token's one-repository scope and the repository's rules; spellings only (a renamed repository is not matched); an entry ending in `.git` is malformed |
| `CW_TOOLING_REPO` | `OWNER/NAME` of the tooling's own repository: refused even when listed; unset adds no extra check, malformed (including a trailing `.git`) refuses; same environment and spelling-only caveats as above |

The guards of the cloud worker against the Mac agent and CI are in `docs/cloud-guard-parity.md`.

**The report path.** The worker writes its final report as ONE line to the fixed file `/home/worker/report` in the pod (the operator driver adds that instruction to the brief it sends). `report <worker>` reads it with `kubectl exec`; the pod needs no switchboard command. A standalone `report` scrubs token shapes only (it does not know the run's secrets), so a report is text the worker chose to write: keep secrets out of it. The read refuses anything that is not a regular file (a symbolic link or a device the worker put there could name a secret mount): exit `3`, `report refused`. The line is one line of at most 2000 printable ASCII characters: control characters, escape sequences, bidi marks and non-ASCII text become `?`.
**The reaper's stop and its exit.** The reaper stops through the same function, so its stops write the record and the hook's result reaches it (`end_hook` in `run.json`, a second atomic write that never blocks the stop); each pass prints `pushed`, `wip_branch`, `skipped` and `record` beside `worker`, `reason`, `exit`. A reaper process that exits writes ONE stderr line `cloud-worker: <UTC ISO time> reaper exiting: WHY` (end of its pass, a signal, an interrupt, an error, or `cluster login failed: ...`). Run as a managed process (opt-in service, `cloud/launcher/README.md`), the service restarts it.

**The run record (one function: the launcher's `stop`).** Every `stop`, whoever calls it (the `run-task` driver on every end, the switchboard's `retire`, a person, the reaper), writes the record BEFORE the end hook, the pod and its Secrets go; there is no other writer. Call: `cloud-worker stop WORKER --reason TEXT [--record-dir DIR | --no-record]`; the record directory is `--record-dir`, else `$CW_RUN_RECORD_DIR`, else `runs/` beside the audit file. The caller supplies nothing else: `stop` reads the server password and the run secrets from the pod's own mounts (`kubectl exec POD -- cat /run/cw/...`, which the operator role may do), opens its OWN `kubectl port-forward` to the pod's server (loopback, closed before `stop` returns), reads the newest session's messages (`CW_RECORD_TIMEOUT`, default 30 s per wait of the server's health poll) and scrubs each STRING VALUE (and key) of each message with the launcher's one `scrub`, so every line stays valid JSON. It writes `transcript.jsonl` (one message per line; at most `CW_RECORD_MAX_BYTES`, default 5 MiB, then a `TRANSCRIPT CUT` marker line; a message over 200,000 characters becomes a `MESSAGE CUT` marker line), `tally.json` (tool calls by tool name and turns, no content) and `run.json` (worker, repository, start, end, exit reason, head sha when known; `transcript: unavailable` and a reason when the server could not be read) to `<root>/<run id>/` (`<worker>-<UTC time>-<6 hex>`; directory `0700`, files `0600`, each written as `.part` then renamed). The root is created `0700`; a root that is a symbolic link is refused (no record; the stop goes on). **One deadline bounds the whole record phase:** `CW_RECORD_SECONDS`, default 90 s, hard maximum 240 s (a larger value is cut to it; zero, negative or unparsable falls back to 90), against the stop's 600 s. Every kubectl call (the secret reads and the head sha) is given only the time that is left, the body is read in chunks with the clock checked on each, a watchdog closes the connection at the deadline and the port-forward is killed. When it passes, the record says `transcript: unavailable` with the reason `record timed out` and the stop goes on to the end hook and the delete: a worker that sends one byte at a time, or answers slowly, cannot keep its own pod. A record that fails, in any way, never holds the stop back (the body is size-capped at 8 MiB and its nesting depth at 100 BEFORE it is parsed; anything else caught is `transcript: unavailable`), and a failed stop never deletes a record. The stop's audit reason and its JSON `record` name the directory once. A pod stopped twice (a kept pod stopped again) gets a record each time. Known limits: the record's port-forward uses a loopback port chosen just before it starts (as the driver's does), so a same-user local process could race for it; a SIGKILL of the launcher mid-record leaves its port-forward running (it holds no secret; kill it by hand); and the report read tests the file and then reads it in one shell script, so a worker that swaps a link in between is not excluded (the line is still scrubbed and one line, and nothing outside the pod's own mounts is reachable by the operator role beyond what it can already exec).
**What the scrub covers.** In a transcript, a planted secret is removed as its whole value, base64 and base64url (padded or not, at each alignment), hex, percent-encoding, JSON escapes of the whole value, and any piece of 8 or more characters of any of those forms (so it holds when split over fields, lines or 8-character pieces; keys are scrubbed as well as values). It does NOT cover per-character escapes (`\u0067\u0069...`, `%67%69...` spelled one character at a time) pieces shorter than 8 characters (4-character pieces reassemble), or a secret written reversed, as HTML entities (`&#103;...`) or letter-spaced (`g h p _ ...`). Token-shaped strings (`ghp_...`, JWTs, 40+ character base64/hex runs) are removed whether or not they are known. All text is reduced to printable ASCII: a non-ASCII character in a transcript or report becomes `?`.
**Retention.** Nothing deletes a record by itself: it is the whole scrubbed transcript of an agent working in a product repository and it stays under the operator's own directory until the operator removes it. `cloud-worker prune-records [--days N]` removes the per-run directories (named like a run id, holding only this tool's three files) older than N days, default 30 (`CW_RECORD_KEEP_DAYS`); a link, a stray file or any other directory in the root is left alone, and a root that is a link is refused. Run it from cron if you want a rolling window.
**`stop --run-id NONCE` (stop by the run's nonce).** The nonce is the `--run-id` the same run gave `create`, which `create` records on the pod (annotation `cw/run-id`) and on both Secrets (label). With it, `stop` acts only on what carries it: a pod that carries it is stopped as usual and only the Secrets that carry it are deleted; a pod of that name that carries another nonce (or none) is another run's, so nothing is stopped, written or deleted, `stop` says `does not match` and exits `6`. With no pod, only this run's own Secrets (left by a cut-off `create`) are deleted; another run's are left whole and the exit is `0`. Matching is exact (a prefix or an extension of the nonce does not match). The audit line's `reason` names the nonce (`run-id=NONCE`) and its `worker` names the worker; a mismatch writes an `ok: false` line the same way. A caller that stops after a failed or cut-off `create` (`run-task`, and the switchboard's launch path through its `_stop_after_failure`) passes the nonce its own `create` was given, never one read from the environment or from the worker. **By name, on purpose:** a `stop` with no `--run-id` acts by worker name exactly as before; the switchboard's `retire NAME`, a person and the reaper use it, because they are the operator's explicit act on a named worker and hold no run's nonce.

A command is idempotent: a repeated `stop` or `delete` of a worker that is gone exits `0`.

## 2. Worker environment (slices A and B)

Injected at start, as environment variables (all non-secret):
`CW_WORKER` (name), `CW_REPO`, `CW_BRANCH`, `CW_IDLE_SECONDS`, `CW_HARD_DEADLINE` (ISO UTC),
`CW_TOKEN_ENDPOINT` (the URL where the worker mints a short-lived GitHub token, authenticated by the pod's federated
identity), `CW_AUDIT_RUNTIME_ID`. The per-worker server password is the one value injected as a file
(`/run/cw/server-password`, mode 0600, from a cluster secret scoped to the pod), never as an environment variable; per-run secrets from `--run-secret-fd` are further files under `/run/cw`. The image entrypoint installs them without printing a value: `model-auth` is copied (mode 600) to a tmpfs data directory, `git-token` is read at call time by a credential helper (https://github.com only) and a `gh` wrapper, and `server-password` becomes the server's `OPENCODE_SERVER_PASSWORD`; a present file that is unreadable or empty refuses the start. The operator driver `cloud/launcher/run_task.py WORKER OWNER/NAME BRANCH BRIEF_FILE` runs one task end to end and cleans up in a normal end, a failure and an interrupt (see `cloud/README.md`).

**Never stored**, in the image, an environment variable, a file on the pod's disk beyond the password above, or a log:
a personal access token, a cloud key or client secret, a registry password, a model API key. Tokens are minted at start
and on demand from `CW_TOKEN_ENDPOINT`, live at most 60 minutes, and are held in memory or a tmpfs. Slice A ships a
scan that fails the image build when any stored credential, host key or build user is found.

## 3. Endpoint record and the switchboard mapping (slices B and C)

Owned by the switchboard (slice C), in its state directory, mode 0600 (a JSON file per worker, path built only from the validated worker name). Slice B never touches the file: `create`, `extend`, `stop` and `delete` print their result and C applies it to the record. The record's deadlines are the source of truth; the pod's `CW_HARD_DEADLINE` is its start-time copy and the reaper re-reads the record.

```json
{"worker": "coder7", "url": "https://worker-coder7.example.internal:4096", "auth_ref": "file:<state>/cloud/coder7.password",
 "runtime_id": "pod/coder7-7f9c", "idle_deadline": "2026-10-14T12:10:00Z", "hard_deadline": "2026-10-14T14:00:00Z"}
```

`auth_ref` names where the switchboard host keeps its own copy of the password (a file path the switchboard chooses itself under its state directory; whatever the launcher prints for it is ignored; it is never taken from caller input, mode 0600: it protects only against other local users); the record never holds it. The pod's copy (`/run/cw/server-password`) is a separate file on the pod side. `create` returns the password once, on a file descriptor named in its output, for C to store. C creates the record from `create`'s output and removes it after `stop` or `delete`.

| Switchboard verb | On a cloud worker |
|---|---|
| launch | `create`, then the existing session create and brief, against `url` instead of the loopback service file |
| send / wake | the same session API call as local, against `url` with Basic auth from `auth_ref` |
| read / status / reports | the same reads (and event stream), against `url` |
| retire | `stop`; the retire says the WIP branch if work was pushed, and fails with `stop`'s exit 1 reason if not |

Today `V2Http` accepts only a `http` loopback address and one service file. Slice C must generalise it to one
endpoint per agent, allowing `https` to a non-loopback host only when the record names one (the password goes nowhere
else). Reachability is over a private network and a TLS proxy (A and B own that; **OPEN**: exact topology).

## 4. Audit line (slice B; mirrored into the switchboard audit log by C)

One line per `create`, `stop`, `extend` and `delete`, appended before the action returns, JSON, no secret:

```json
{"ts": "2026-10-14T12:00:00Z", "worker": "coder7", "runtime_id": "pod/coder7-7f9c", "action": "create", "cost_estimate_usd": 0.07, "ok": true, "actor": "operator", "reason": ""}
```

`cost_estimate_usd` is the list-price estimate of the pod so far (zero on create; elapsed hours times the shape's rate
on the others). It is an estimate, not a billed figure. A failed action still writes its line with `"ok": false`. `actor` is taken from the session, never from an argument; `reason` carries `--reason` (for `stop`, `extend` and `delete --force`).

## 5. End hook (slices A and B)

Runs inside the pod on `stop`, a hard deadline, an idle stop and a node drain notice, before anything is deleted:
1. If the working tree has uncommitted changes, commit them (files matching the secret-scan patterns and the ignore list are left out, and the hook reports them) on a WIP commit; if HEAD is on no remote branch, push it to `<worker>/wip`.
2. Push success: report `{pushed: true, wip_branch}` and let the launcher delete the pod.
3. Push failure: **keep the pod**, report the reason, and `stop` exits `1`. The pod stays until `delete --force` or its next stop succeeds. A kept pod still obeys the hard limit's cost cap (**OPEN**: whether a kept pod may exceed the hard limit, and who is alerted).

A clean tree whose HEAD is already pushed pushes nothing and reports `pushed: false`.

### The retire path: how the end hook pushes (#1018)

**Cause.** The end hook runs inside the pod and, before this change, pushed with the credential the pod was started with: the per-run `git-token`, a one-hour App installation token minted at launch. When that token has expired (a pod older than an hour, or the App was re-created), `git fetch` failed with an authentication error, the hook exited 1, `stop` kept the pod, and the retire was refused with the work stranded in the pod.

**Rules now.**

- **Fresh token.** When this launcher can mint (`CW_GIT_TOKEN_CMD`, or the vault/App settings `app_token.py` reads), `stop` mints a fresh one-repository token at retire time, from the repository recorded on the pod (`CW_REPO`), only when the hook is about to run. It goes to `cw-end-hook --token-stdin` on the standard input of the `kubectl exec -i`, is held in memory only, and is used for the hook's own `git fetch` and `git push`. It is never an argument, never in the pod's environment after the push, never written to a file, a Secret or the run record, and never printed. The token is offered to `github.com` only (never to the host an agent-writable repository config names), and git runs with hooks, a file-system monitor, an askpass program and a proxy switched off for those two calls. A pod that records no repository cannot be minted for: that is a mint failure. A launcher with no mint settings, and an image whose hook predates the flag, behave as before.
- **Keep, and say so once.** If the mint fails, or the push still fails, the pod stays marked `cw/kept=true`, nothing is deleted (the pod, both Secrets and the run record stay), and `stop` says so once on stderr: the step that failed (`mint` or `push`, never the detail), that the pod and its work are kept, and the recovery route below. A later `retire` mints again.
- **Never cloned.** A pod whose default checkout `/work/repo` was never made (the clone failed) answers `pushed: false` with the note `no checkout; nothing to push`, and the retire ends the worker. A directory that exists but is no repository is an error: the pod is kept. An explicitly set `CW_WORKDIR` that is missing is also an error.
- **Secrets' lifetime.** Unchanged: the per-run Secrets go with the pod on a successful retire, and a kept pod keeps its dead token Secret until `delete`; a dead token is not a credential, and the fresh token is never stored, so there is nothing new to expire.

**Recovery route (read-only; run it from the operator's machine).** It reads the pod and deletes nothing; decide afterwards whether to push or to `delete --force`.

```sh
kubectl exec POD -- git -C /work/repo bundle create - --all > worker.bundle    # the commits
kubectl exec POD -- tar -C /work -cf - repo > worker-repo.tar                  # the files that were never committed
git clone worker.bundle recovered                                              # locally
```

## 6. Idle and hard limit

- **Idle** = no tool call and no model activity (a running session or step) for `CW_IDLE_SECONDS`. Inbound
  requests, health checks and event-stream reads do **not** count as activity: a worker that is only being watched is idle.
  A worker mid-task (a long build, a waiting model call) is not idle. The reaper reads this from the worker's own session state.
- **Hard limit** = `CW_HARD_DEADLINE`, absolute. At the deadline the end hook runs and the pod is stopped,
  whatever the activity. `extend` is the only way to move it; the reaper re-reads the record at each pass.
- **Cluster-side floor.** Every pod the launcher builds (shapes S and M alike) sets `spec.activeDeadlineSeconds` to the
  `--max-hard` cap plus `POD_DEADLINE_GRACE_SECONDS` (300 s; the cap's default is 8h, so always finite). The kubelet then ends
  the pod even when no reaper runs. It is the cap, not the current hard limit, because Kubernetes lets that field be lowered
  on a running pod but never raised: a value at the initial hard limit would make `extend` within the cap impossible. The grace
  lets the reaper, which writes the run record and runs the end hook, normally act first. A pod the floor ends has phase
  `Failed` and reason `DeadlineExceeded`: no hook runs and unpushed work is lost, so the floor is a last resort. `stop` and the
  reaper treat a `Failed` pod as already ended and delete it and its Secrets (the run record is still written first).
- Both stops are checked at least every minute and take effect within 3 minutes of the limit (plan scenarios S2, S3).
- **OPEN**: how a worker asks for its own extension (a command inside the pod, or only an operator).

## 7. How the switchboard reaches the cloud (wiring)

`launch --cloud`, `send`, `read`, `status` and `retire` reach the cluster with a token of at most one hour minted from the
administrator credential in the vault at the moment of use (`CW_CLUSTER_TOKEN_CMD`, or the vault default; see
`cloud/launcher/README.md` for the settings). No token and no tunnel is kept between commands: the token lives in a private
0600 file for one command, and `send`, `read` and `status` open a port-forward that is closed before they return. A missing vault
is a refusal (exit 2) that names the vault pre-check. Only repositories on `CW_ALLOWED_REPOS` can be launched.

**What the pod is told.** The session is created in `/work` (the scratch volume; `--dir` overrides) with the image's own agent, `worker` (`cloud/worker/agents/worker.md`), whatever `--agent` says: for `launch --cloud`, `--agent` is the local role name and is only recorded in the endpoint record. The brief is sent after a standard setup preamble: clone the repository into `/work/repo`, switch to the task branch, work only there (the end hook pushes from `/work/repo`). `retire` of a worker whose end hook cannot push keeps the pod and the record; `cloud-worker delete NAME --force` is the explicit last resort and discards the pod's work.
