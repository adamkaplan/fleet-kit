## The cause (clause 1, stated first)

A lane's first database-lane test in a stack pod needed Node and npm. The worker image carries neither (its Dockerfile installs python, git, docker and a standalone opencode binary, no Node). The coder therefore downloaded a Node tarball into its home directory and installed the repository's dependencies from there, at every launch, unverified. The pull request body opens with this paragraph.

## Open choices (one recommendation each)

(a) Version and checksum. Recommend two named build arguments at the top of the Dockerfile, in ONE place: NODE_VERSION (a full 22.x.y release, major 22) and the checksum source (the release's SHASUMS256.txt address, derived from that version). The build downloads the tarball for the image's architecture (the build's `dpkg --print-architecture` mapped to x64 or arm64) and the SHASUMS256.txt, checks the tarball's entry with `sha256sum -c` BEFORE `tar -x`, unpacks to /opt/node (root-owned) and links node, npm and npx into /usr/local/bin (on the default path). Same pattern as the opencode step already in the Dockerfile. Alternative: pin each checksum as a constant; rejected for one more value to bump per architecture. The offline test reads the Dockerfile text only.
(b) prettier and eslint. The ask #1040 does not name them: they are dev dependencies of a repository, not of the image, so the image does not install them and #1040's Done-when is NOT widened. One scenario (S6) shows the image's npm runs a repository's own installed prettier and eslint through npx without downloading a runtime. For the Chief of Staff: say if the image should instead carry them globally (recommendation: no).
(c) Unpinned channels. No apt nodejs, no NodeSource script, no `npm install -g` of a floating tag.
