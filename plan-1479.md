# Plan for #1479: config: relay_holders is a known key

plan-format: 2
size: S

Canonical issue: https://github.com/adamkaplan/fleet-kit/issues/1479

Intent: The switchboard stops warning that relay_holders is a key it does not read.

## Done-when

Done when: a config.json with relay_holders loads without the 'does not read: relay_holders' warning, and the key's shape is validated (an object mapping repo#issue to a pod name).

## Constraints

- PC-1: loading a config without relay_holders is unchanged (reason: most installs have no relay).
- PC-2: the unknown-key warning stays for every other unknown key (reason: it catches typos).
- PC-3: the relay daemon's own reading of relay_holders is not changed; the validated shape is the one it already reads (repo#issue key to pod name).
- PC-4: the error is a named ConfigError, in the style of the existing validation of small keys such as plan_evaluators and the declaration list in config_declarations().

PC-3 and PC-4 are checked by review of the diff rather than a scenario of their own beyond S2 to S5; no scenario cites them to keep the plan light.

unchanged: see U1 and U2.

## Out of scope

- Any change to bin/cloud_relay_daemon.py.
- Validating that the pod named exists, or that the repo#issue exists.
- Other unknown keys, other config keys, defaults.

## Areas touched

- bin/fleet-switchboard (validate_config, config_declarations): a held-PR area, so the pull request needs the held-area approval (cos).
- docs/switchboard.md (config section): document the key and its shape.
- tests: new cases for the scenarios above.

## Risks and rollback

- Risk: a real config with a shape the daemon tolerates but the new check refuses (for example a key without '#') now fails loading. Mitigation: the shape is the one the daemon documents; the error names the key.
- Rollback: revert the single pull request; the warning returns and nothing else changes.

## Open questions

- Should a malformed relay_holders stop the load (ConfigError, as the issue says) on a running install, or only warn? Plan assumes ConfigError per the issue.
- Is surrounding whitespace in a pod name trimmed or rejected? Plan assumes whitespace-only is rejected and nothing is trimmed.

## Size and tier

size: S (under 1 hour; one held file, one doc, a few tests). Stay on main; no integration branch.
