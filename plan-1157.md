## The cause (clause 1, stated first)

`cloud/worker/entrypoint.sh` writes only `worker.md` (copied from the share directory) into the agents directory, and in `bin/cloud_worker.py` `cmd_launch` (about line 1202) `args.agent` is only recorded, never passed to the pod. So no pod can run an orchestrator. The pull request body opens with this paragraph.

## Design

- ONE allow-listed value `CW_AGENT` (`worker` or `orchestrator`; unset means `worker`). Any other value: the entrypoint exits with a named message before the server starts; the launcher refuses it earlier still.
- Three fixed non-secret names: `FLEET_AGENT_NAME`, `FLEET_BOSS`, `FLEET_CLOUD_CHANNEL_URL`. The channel address is a row in the launcher settings file (non-secret; the settings-table rule applies). Passed only when the agent is `orchestrator`.
- Per-pod channel credential (DW-5): a PER-POD RANDOM SECRET written by the launcher into the pod's per-run Secret as ONE new key (the channel secret), like the model credential: it expires with the pod, is never printed, only its sha256 is stored on the hub side, and it is mounted on the existing memory-backed directory. The pod gets one more fixed non-secret name `FLEET_CLOUD_TOKEN_FILE` (the path of that file; the cloud command reads any file named by it). Tightening-only boundary, stated in the pull request. There is NO projected service-account token volume and NO cluster RBAC: no new volume is admitted.
- Fixed values (hub lane): `FLEET_CLOUD_CHANNEL_URL` is a settings-file row, non-secret, default `http://cloud-hub.cw.svc:8443`. `FLEET_CLOUD_TOKEN_FILE` is `/run/cw-tmp/fleet-switchboard`: a path INSIDE the pod's existing memory-backed directory (the `tokens` in-memory emptyDir mounted at `/run/cw-tmp`), not the hub lane's suggested `/var/run/secrets/tokens/fleet-switchboard`, because no new volume or mount is admitted. The per-run Secret (mounted read-only at `/run/cw`) gains the key `channel-secret`; the entrypoint, for an orchestrator only, installs it from `$RUN/channel-secret` to the memory-backed file with mode 0400 owned by the worker user (a copy by `install`, never a symlink, never printed). The cloud command reads whichever file `FLEET_CLOUD_TOKEN_FILE` names.
- Per pod the launcher: generates 32 random bytes (64 hex characters) as the channel secret; puts it in the per-run Secret; REGISTERS the pod with the hub by adding `{agent name: sha256 hex of the secret}` to the hub's secrets map and `{agent name: {url, session, password_file}}` to its agents map (two JSON documents the hub reads at each request); at stop REMOVES both entries; a failed registration refuses the launch and removes what the launch created (like the other launch refusals). Only the sha256 is ever stored on the hub side. The registration is the one new launcher write to the cluster. The hub (Deployment `cloud-hub`, Service port 8443) is NOT part of this ask: only the launcher side and the pod side.
- The env allow-list admits exactly five new names: `CW_AGENT`, `FLEET_AGENT_NAME`, `FLEET_BOSS`, `FLEET_CLOUD_CHANNEL_URL`, `FLEET_CLOUD_TOKEN_FILE`; the per-run Secret gains exactly one key. `CREATE_OPTION` gains the agent value. No new token role.

## Open choices (one recommendation each)

1. **Files copied into the image.** The Docker build context is `cloud/` only, so a file outside it cannot be COPYed. Recommend: a BYTE-IDENTICAL tracked copy under `cloud/worker/` of each of `bin/cloud_cli.py`, `bin/cloud_client.py` (integration branch, PR 1150), `agents/opencode/orchestrator.md` (the orchestrator definition, copied to `cloud/worker/agents/orchestrator.md`, no repository-specific text), and for the hub `bin/cloud_hub.py`, `bin/cloud_channel.py`, `bin/cloud_channel_server.py` (PR 1152); all land on the integration branch. One CI drift test compares each copy to its source byte for byte and fails on any difference. Alternative: widen the build context to the repository root; rejected, it puts the whole repository in the image build. The image rebuild is ONE rebuild covering all of them, by the operator after merge.
2. **Where the refusal lives.** Recommend a pure check at the top of `cmd_launch` in `bin/cloud_worker.py` before any cluster, vault or token call, with the entrypoint check as the second line.
3. **Where the registry lives.** Recommend ONE Secret `cloud-hub-registry` in the `cw` namespace with two keys, `secrets.json` and `agents.json`, patched by the launcher's own cluster login (name and namespace from the settings file). Alternative: a ConfigMap; rejected, the sha256 map is credential-adjacent and a Secret keeps the read rules tight. Registry writes are read-modify-write of one key with the resourceVersion check, so two concurrent launches do not lose an entry.
4. **Add one line to `cloud/worker/agents/worker.md`** saying the agent is chosen by `CW_AGENT`.

## Out of scope

The orchestrator token role (ask 1068), the orchestrator role itself, the hub Deployment and Service and its code (PR 1152; the hub reads the registry, this ask only writes it), the cloud command (PR 1150).

## Risks and rollback

A wrong allow-list widens the pod; S6 and S7 guard it. Rollback is revert and an image rebuild; the worker default is unchanged so existing pods are unaffected. Integration branch: stay on the existing integration branch where PR 1150 and 1152 land.
