## The cause (clause 1, stated first)

`cloud/worker/entrypoint.sh` writes only `worker.md` (copied from the share directory) into the agents directory, and in `bin/cloud_worker.py` `cmd_launch` (about line 1202) `args.agent` is only recorded, never passed to the pod. So no pod can run an orchestrator. The pull request body opens with this paragraph.

## Design

- ONE allow-listed value `CW_AGENT` (`worker` or `orchestrator`; unset means `worker`). Any other value: the entrypoint exits with a named message before the server starts; the launcher refuses it earlier still.
- Three fixed non-secret names: `FLEET_AGENT_NAME`, `FLEET_BOSS`, `FLEET_CLOUD_CHANNEL_URL`. The channel address is a row in the launcher settings file (non-secret; the settings-table rule applies). Passed only when the agent is `orchestrator`.
- Per-pod channel credential (DW-5): the channel needs one, so the chosen route is a PROJECTED SERVICE-ACCOUNT TOKEN VOLUME: audience is the hub's name from the settings file, expiry 600 s, the pod's own service account, mounted read-only at one fixed path the cloud command reads. It is a new named volume and mount constant in the stack-pod allow-lists in `cloud/launcher/cloud_worker.py` (beside `STACK_VOLUMES` and `STACK_MOUNT_PATHS`) and the env names are added to the env allow-list (beside `ALLOWED_ENV_NAMES`); nothing else is widened. `CREATE_OPTION` gains the agent value. No new token role.

## Open choices (one recommendation each)

1. **Files copied into the image.** The Docker build context is `cloud/` only, so a file outside it cannot be COPYed. Recommend: a BYTE-IDENTICAL tracked copy under `cloud/worker/` of each of `bin/cloud_cli.py`, `bin/cloud_client.py` (integration branch, PR 1150), `agents/opencode/orchestrator.md` (the orchestrator definition, copied to `cloud/worker/agents/orchestrator.md`, no repository-specific text), and for the hub `bin/cloud_hub.py`, `bin/cloud_channel.py`, `bin/cloud_channel_server.py` (PR 1152); all land on the integration branch. One CI drift test compares each copy to its source byte for byte and fails on any difference. Alternative: widen the build context to the repository root; rejected, it puts the whole repository in the image build. The image rebuild is ONE rebuild covering all of them, by the operator after merge.
2. **Where the refusal lives.** Recommend a pure check at the top of `cmd_launch` in `bin/cloud_worker.py` before any cluster, vault or token call, with the entrypoint check as the second line.
3. **Add one line to `cloud/worker/agents/worker.md`** saying the agent is chosen by `CW_AGENT`.

## Out of scope

The orchestrator token role (ask 1068), the orchestrator role itself, the hub and channel code (PR 1152), the cloud command (PR 1150).

## Risks and rollback

A wrong allow-list widens the pod; S6 and S7 guard it. Rollback is revert and an image rebuild; the worker default is unchanged so existing pods are unaffected. Integration branch: stay on the existing integration branch where PR 1150 and 1152 land.
