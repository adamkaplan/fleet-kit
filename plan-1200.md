## The pull request edit mechanics (open choice, recommended)

The client reads the pull request first (`GET pulls/N`: head branch, base repository, current body). It refuses (row `pr-edit-read-failed`) when the read fails or does not parse; refuses when the base repository is not the worker's repository or the head branch is not the worker's own branch (the branch the pod started on; the record of pull requests it created is a second source, not required); refuses when the current body has the exact line `MERGE: captain` and the new body does not hold that line exactly once unchanged; then makes one PATCH of the body only. The allowed command is exactly `pr edit N --body-file F`.

## Family and sequence

One guard family, one table, one image rebuild. Order: #1083 first (creates the table `cloud/worker/guard-table.tsv`, the single source read by both `cloud/worker/guard.sh` and `cloud/worker/cw-gh`, and the agreement test `cloud/worker/tests/test_guard_table.py`), then #1166, then #1200. Each ask adds only its own rows, named below, so no row is duplicated:

- #1166 rows: `issue-comment-create` (the `issue comment` verb and POST to issues/N/comments), and the denied rows `issue-edit`, `issue-create`, `issue-close`, `issue-reopen`, `issue-lock`, `issue-unlock`, `issue-delete`, `issue-transfer`, `issue-pin`, `issue-labels`, `issue-assignees`, `comment-patch`, `comment-delete`, `api-method-flag` (-X / --method), `api-write-other`.
- #1200 rows: `pr-edit-body-file` (allowed, own pull request only) and the denied rows `pr-edit-inline-body`, `pr-edit-other-option`, `pr-edit-other-number`, `pr-edit-url-other-repo`, `pr-edit-api`, `pr-edit-no-hold-line`, `pr-edit-read-failed`.
These asks build in the same sequence and the same image rebuild, together with ask 1040, ask 1165 and the daemon lane's pr-explain template (no overlap of rows with them). The live checks run once, after that rebuild, hence `claim: epic`.

## Open choices (one recommendation each)

1. **Where the table lives.** Recommend one file `cloud/worker/guard-table.tsv` (columns: id, allowed|denied, tool, verb or method, path pattern, exact refusal text). Both programs read it at run time; the `opencode-worker.json` patterns are generated from or checked against it. A test runs every row through the guard and through the client and fails on any difference. Alternative: a table inside the client, rejected because the shell guard must stay shell only and cannot import it.
2. **Build order.** As above; the first ask creates the file and the test, the others only append rows.
3. **Denied-form strings.** One line `refused: <row id>: <fixed phrase>: the repository's rules are the guard; this wrapper is only a convenience`, as the guard prints today; no argument value is ever printed; exit status 3, before any network call.
4. **Token.** No new token permission is requested by this ask except as stated in the clause on the token; the token already holds pull requests write.
5. **Held.** The worker's shell guard and token paths are credentials-class: the pull request is HELD for the owner. The impact floor expects the owner's approval, never delegated, a mutant for each denied row, and the image rebuild on the Chief of Staff's word.
