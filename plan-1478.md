# Plan for #1478: a cloud pod's report reaches its boss without a herdr pane

plan-format: 2
size: M (about 3 files, one held area; the risk is the sender identity in the engine, not the volume)

Canonical issue: https://github.com/adamkaplan/fleet-kit/issues/1478
Evidence: S13 live proof (#1363). The relay's `report` command calls `SwitchboardBackend.report` (bin/cloud_relay_daemon.py), which calls the engine's `report(pod, state, text, issue, False)` (bin/fleet-switchboard). The engine looks the sender up in `discover()` (herdr panes with a v2 session), finds none for a cloud pod and raises ReportError "s13-holder not found: no herdr pane shows a v2 session named s13-holder". The daemon then audits relay.failed. The relay already claims the call id first (PENDING), delivers, then marks done, so the at-most-once frame exists; only the delivery step fails.

## Done-when

(1) from a probe pod, a relayed report is delivered to the boss once (at most once), and (2) the daemon's audit shows it with the pod's name, with no relay.failed.

```yaml

```

(Joined: "from a probe pod, a relayed report is delivered to the boss once (at most once), and the daemon's audit shows it with the pod's name, with no relay.failed" = the issue's Done-when, split at its own comma-and.)

## Outcomes (what a pod's report must be)

- O1: a pod with a registry row (kind cloud, with an endpoint) and no pane can report; the engine does not need a pane or session to know the sender.
- O2: the sender shown to the boss, in the fact and in the audit, is the pod's name.
- O3: the boss is the pod's registered boss (its registry row or fleet metadata `reports_to`); a pod with no boss gets the engine's existing "reports to nobody" refusal, not a pane error.
- O4: the boss receives exactly what a local report gives: an attention state (done, failed, blocked, question) is delivered now with the waiting progress riders; a progress state (working, paused, withdrawn) is recorded as a rider and sent with the next message. Same text limits, same state validation, same issue resolution.
- O5: at most one delivery per (pod, call id): a replay of the same call id, or a retry after a lost answer, delivers nothing more (the relay's claim stays the guard; the engine adds no second key that could double-deliver).
- O6: a refusal (unknown pod, bad state, unreadable boss) is audited as a refusal with the pod's name and the reason, never as a pane-not-found.

## Smallest design (constraint-free; the implementer may pick another that meets the outcomes)

Let the engine's `report` resolve the sender from the registry when discovery has no observation and the registry row is a cloud row: build a minimal sender record (name, fleet metadata with reports_to/repo/issue from the row) and go on through the same code (Fact, rider, send_fact). Delivery to the boss uses the existing send path, which already puts a pod's messages into the Mac daemon's inbox. Pane-bearing senders take the old branch untouched. Where #1182 (pane-less liveness on integration) has landed, reuse its row reader rather than adding another.

## Constraints

- PC-1: a local (pane) report behaves exactly as before: same fact key shape, same rider, same ReportError text for an unknown local agent. Reason: every agent uses it.
- PC-2: only an agent whose registry row is a cloud row is resolved without a pane; any other unknown name keeps the "not found" refusal. Reason: a pane-less name must not become a way to forge a sender.
- PC-3: the relay's other commands (gates, prove, verdict, send path, the claim/done ledger) and the relay's authentication of the pod name are unchanged. Reason: the pod name comes from the authenticated hub call, never from the request body.
- PC-4: no credential, token or endpoint secret appears in the fact, the audit or logs.

## Out of scope

Pod-to-pod messages, the hub's `send` path, pane-less liveness itself (#1182), report folding changes, the worktree reclaim on done (a pod has no registered worktree; it must be skipped, not fail), new relay commands.

## Areas touched

- bin/fleet-switchboard (engine `report`, sender resolution): bin/ is a held-PR area.
- bin/cloud_relay_daemon.py (only if the backend must pass the pod's registry facts; the daemon executor is in a held area): held-PR area.
- bin/test-cloud-relay-daemon (or a new test next to it) and the registry reader if #1182 is not yet in.

## Risks and rollback

- Risk: a pane-less sender accepted too widely (PC-2, S5). Risk: the done-report reclaim step runs for a pod (must be skipped). Risk: a duplicate on retry if the engine key differs per attempt (S2).
- Rollback: one revert of the PR; the relay then fails reports as it does today, with no data change.

## Open questions

1. Where is the pod's boss recorded: the cloud registry row's `reports_to`, or fleet metadata at pod creation? If neither, the hub must supply it, which widens the change.
2. Does #1182's row reader exist on main yet, or must this wait for or follow the integration branch?
3. Should a progress rider from a pod be shown to the boss under the pod's name or under its issue? (Plan says the pod's name.)

## Integration-branch decision

Stay on main unless #1182's row reader is needed and only on its integration branch; then branch from that integration branch.
