# Plan: #1225 cloud hub relay (report, prove, verdict, gates from a pod)

plan-format: 2

## What exists today (read)

- `cloud/worker/bin/cloud_hub.py`: the hub. `POST /message` (token review via per-pod sha256 secrets file `FLEET_CLOUD_HUB_SECRETS`, or TokenReview; sender pinned to the verified agent; `Inbox.put_if_absent` delivers to the agent's session; LRU in-memory dedupe) and `GET /decisions`. Identity is already "the pod's per-pod secret -> agent name" (`make_secrets_reviewer`).
- `bin/cloud_channel.py` (`handle`: 401/403/400/503 rules, `agent_of`) and `bin/cloud_channel_server.py` (`/message` route only, 404 for any other path, `MAX_BODY`, deadlines, reserved names).
- `cloud/worker/bin/cloud_cli.py`: pod side, `send` and `report KIND TEXT` (the latter is only a `send` to the boss, NOT the switchboard `report`). No `prove`, `verdict`, `gates`.
- Local commands in `bin/fleet-switchboard`: `cmd_report` (engine.report, delivered like send, no ledger line), `cmd_prove` and `cmd_verdict` (write hash-chained proof/verdict entries through `plan_ledger.append_checked` / `append_many` under the ledger flock, `by` = `identify_caller`, `head` from `_head_of`, plan hash from the PR's plan, audit line `plan.verdict`), `cmd_gates` (read-only `evaluate_gates`). All four identify the caller by pane/session, which a pod does not have.
- Hub has no GitHub token and no state directory; the daemon on the Mac owns the ledger and the GitHub token. So the relay is hub -> daemon.

## Design (outcomes; how stays with the worker unless a constraint)

Path for the ledger line: pod -> hub (authenticates, pins identity, checks the allow-list, size, call id, repo/issue binding) -> **daemon** (the only writer of the ledger and the audit; it re-validates head against GitHub, runs the same rule code as the local command with the pod's name as the caller, appends the one entry) -> answer back along the same path. The hub never writes a ledger entry and holds no GitHub token; the pod never sees one.

Constraints:

- PC-1: Identity comes only from the per-pod secret. The record's `by` is the pod's own name as the hub resolved it, never a name in the body and never the pod's orchestrator. Reason: evaluator and author-exclusion rules (`may_record_verdict`, `authors_of`) depend on who wrote what.
- PC-2: Every `prove` and `verdict` request names the PR head it judged; the daemon compares it to the PR's live head and refuses if it moved (no record, answer says so). `--all` style batches need an explicit head, as locally.
- PC-3: One record per call. A call carries a call id (client-chosen, bounded printable ASCII, scoped to the verified pod, like the existing key). A replay with the same call id returns the SAME record (same seq and hash) and writes nothing new. The memory of call ids must survive a hub restart for records already written: the daemon, not the hub's in-memory LRU, is the source of truth (lookup by pod+call id in the ledger entry or a daemon-side index).
- PC-4: Refusal list, each answers a distinct status/reason and writes NOTHING (no ledger entry, no partial batch): unknown pod, wrong secret, wrong repo or issue (the pod's bound repo/issue from the hub's agents map, not the body), stale head, a command not in {report, prove, verdict, gates}, an oversized body. Missing call id and malformed fields are also refused (400). Each refusal leaves one audit line without the secret.
- PC-5: No GitHub token enters the pod, the hub's environment, the request, the answer or any log. The hub-to-daemon hop carries only the verified pod name, repo, issue, command, args, call id.
- PC-6: `gates` is read-only: it answers the gate report for the pod's bound PR and writes no ledger entry; the daemon still writes its audit/ledger line recording that the pod asked (kind distinguishable from a proof or verdict), exactly one per call.
- PC-7: The existing `send` path and `GET /decisions` are untouched: same routes, same statuses, same bytes.
- PC-8: The local `fleet-switchboard report|prove|verdict|gates` keep their behaviour; relay code reuses their rule functions rather than copying them, and does not change their output.

## Out of scope

- The issue-comment half (#1166). Other commands (`notice`, `plan check`, `gates ci-record` and the rest of the switchboard CLI): refused, not relayed.
- Changing how `send` reaches an agent, how secrets are issued or rotated, or the local identity rules.
- Persistence beyond what PC-3 needs; relaying to more than one daemon; any GitHub write from the hub.
- Product code in this plan's PR (this PR is the plan only).

## Areas touched

- `cloud/worker/bin/` (cloud_hub.py new routes, cloud_cli.py new verbs, cloud_client.py) and its tests. Not a held-PR area.
- `bin/` is a **held-PR area**: the daemon-side executor (in or beside `bin/fleet-switchboard`, plus `bin/plan_ledger.py` if call-id lookup is stored in entries) and `bin/cloud_channel*.py` if the server's route table is extended. The PR touching `bin/` needs cos approval; keep the `bin/` slice small and separate if possible.
- `docs/` (cloud worker interface page).

## Risks and rollback

- Risk: the daemon executor drifts from the local command's rules. Mitigation: call the same functions (PC-8), U1.
- Risk: stale-head race between check and append. Mitigation: re-check the head inside the ledger append decision (`append_checked`), not before it.
- Risk: replay memory lost on restart yields a second record. Mitigation: PC-3, S11.
- Risk: the hub-to-daemon hop becomes an unauthenticated write door. Mitigation: it listens on loopback/private link only, requires a hub-to-daemon credential, and accepts only the four commands from the hub; open question 1.
- Rollback: the relay is off unless the hub is configured with the daemon endpoint (and the pod CLI verbs are new); unset the endpoint and the hub refuses the four commands while `send` is unaffected. Ledger entries already written are append-only and stay valid; revert the PR(s).

## Open questions

1. How does the hub reach the Mac daemon (the pod reaches the hub; the daemon may need to pull a queue from the hub instead of the hub pushing in), and what authenticates that hop?
2. Where is the call-id to record index kept: a field on the ledger entry or a separate daemon-side file?
3. Which PR does a pod's request bind to: the one named in the body, checked against the pod's bound repo/issue, or only the PR linked to its issue?
4. For `report`: is it the switchboard `report` (state rider to the boss) or the existing `cloud_cli report`? This plan assumes the switchboard one, relayed.
5. Integration branch: this plan assumes work stays on main (slices small), unless cos prefers `integration/cloud-hub-relay`.
