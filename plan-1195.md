## The cause (clause 1, stated first)

Over one day a cloud pull request took nine pushes and others two to four. Each cloud coder learned the repository's checks from a red run: a new test file not chained in the launcher's test list, an existing test of another file broken by the change, or an existing pinned test edited to make a new behaviour pass. A cloud pod cannot run the whole suite, so the check has to be a one-file-at-a-time offline command. The same paragraph opens the docs section "Checking a cloud pull request before the push" in `docs/cloud-operator-quickstart.md`.

## Out of scope, risks and open questions

- Out of scope: running the whole suite, changing any product code, writing issues.
- Gap found on the built change: no test records subprocess calls, so "never git stash" and "never the network" are shown by reading the command (it uses git archive, rev-parse, diff, ls-files only), not by a test; nor does a test make the command fail midway and check cleanup (the command removes the copy in a finally block). A reviewer should accept this or ask for those two tests.
- Gap: S12 and S14 need a small test that reads the docs section; the built change has none yet, so it is a follow-up to add to the test file.
- Gap: the shared brief rules for cloud coders (second half of DW-6) are not edited in pull request #1209; they live outside the four files, and need a follow-up edit.
- Note: the command exits non-zero whenever an existing test file is changed (to force a justification), so S8 shows exit status is 1.
- Rollback: delete the command, its test and the chain line; nothing else depends on them.
- Integration branch: stay on main; build after the open cloud pull requests merge, as they edit the same test list.
