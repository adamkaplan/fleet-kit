## Cause (clause 1)

An independent reader of the hub's manifest set found no network policy in the repository while the cluster carries six applied by hand, none in a file today: default-deny, allow-egress, cloud-hub-ingress, cloud-hub-to-agents, cloud-agents-to-hub, cloud-agents-ingress-from-hub.

## Test method

The new test, cloud/launcher/tests/test_cloud_hub_network.py, is chained at the end of bin/test-cloud-launcher. As the first manifest's test does, it drops comment lines, splits on the document separator and reads each part with json.loads (the repository has no YAML library), so the file's bodies are written in JSON-compatible flow style. Mutants are applied to parsed copies.

## Open choices (one recommendation each)

- (a) The public egress exceptions include the Azure platform address 168.63.129.16/32, a generic public platform address, not private. Keep it as applied (recommended) versus naming it in a comment. Recommendation: keep as applied.
- (b) The label cw/run: first-ask on four policies is a leftover run label. Keep exactly as applied (recommended): the file is a copy of the live state, and a changed label would show as a difference on apply.
- (c) Apply order: apply the four hub allow policies and allow-egress BEFORE default-deny, because default-deny first cuts every pod off. First check: a worker pod can still resolve names and the hub answers its health path. Rollback: delete -l app.kubernetes.io/part-of=cloud-hub for the four hub policies, and delete allow-egress and default-deny by name.
- (d) The file's header comment says how it is applied (kubectl apply -f, allow policies first) and how it is rolled back (as in c). Recommendation: write it in the header and mirror it in the operator document.

## Out of scope

Changing any rule, adding policies, cluster-wide policy, workflow files, product code.
