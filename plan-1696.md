Which case is the recorded one: a comment posted with gh api to an issue or pull-request comment endpoint that reached GitHub unsigned. With -f or -F body
(forms a, b, c, i1) that is true on main and FIXED on integration (#1641 and #1646): there is no residual for these. With --input (d, e) it is unsigned
on BOTH, so the residual is: --input forms on the comment and review endpoints (the recorded case if the lane wrote its body as JSON), the
GraphQL body mutations (f, g), and the two endpoint shapes of row j. The ask shrinks to those residuals; DW-1 is therefore a statement about the reproduction plus the two scenarios S1, S2 that fix the claim.
(Whether the recorded case used -f or --input cannot be told from the issue text I could read: both are covered, and the plan does not depend on which.)

Note found while reproducing: when hold_labels is configured, hold_probe already refuses every graphql mutation and graphql --input (bin/test-gh-hold, test_graphql_mutations_cannot_be_tied_to_a_pull_request), so the GraphQL residual is open only where no hold is configured. The signing refusal must not change that existing wording or order.

## 3. Design choice (what, with the cost of each option)

- --input on a SIGNED_API endpoint with a POST or PATCH: read the JSON (file, or stdin when the value is -); an object with a string `body` is signed and
  passed on (a temp file, or stdin, as the -F @file path does today); an object with no `body` key passes unchanged (a review with only an event; no text to sign);
  JSON that cannot be read or parsed, a `body` that is not a string, or a missing file is REFUSED with one line and nothing is posted. Signing, not refusing, is chosen: lanes may use it today (section 7) and a refusal would break them. Cost: S.
- GraphQL: a body-writing mutation is REFUSED with one plain line (no signing). Reason: the text sits inside query text or in variables, so reliable
  signing means parsing GraphQL; a refusal that names the REST or `gh pr comment` form is small and cannot post unsigned. Signing a `$body` variable is the larger option (M) and is left to an open question. The set: addComment, addPullRequestReview, addPullRequestReviewComment, addPullRequestReviewThread, addPullRequestReviewThreadReply, updateIssueComment, updatePullRequestReview, updatePullRequestReviewComment (8 names, a table in the shim). The name is found case-insensitively and also as an alias (a: addComment(...)) and in a query file (-F query=@file) or --input; a query that cannot be read is refused, as the merge route does today.
- Not added (out of this ask, stated so): discussion, commit-comment, createIssue and PR-body mutations; pulls/comments/ID and /replies endpoints (row j).

## 5. Constraints

- PC-1: shims/gh is an owner-only (held) path: the change is not merged by a lane; it is held for the owner. Every refusal is ONE plain line on stderr beginning "gh: " with exit status 1, as the existing "gh: refused: ... so it cannot be signed and nothing was posted" line.

- Discussion, commit-comment, createIssue, updateIssue, createPullRequest, updatePullRequest mutations, and pulls/comments/ID and pulls/N/comments/ID/replies endpoints.
- Any change to review_rule, gh_hold, the merge gate, the read cache or the 5 SIGNED_COMMANDS.
- The switchboard's own writes (they use the real gh by path).
- Any claim about forms of other tools (curl, python) that never touch the shim.

## 8. Rollback and order/risks

Rollback: revert the one commit on shims/gh and the new test file; nothing else depends on it (no data, no config, no doc). An installed shim is a copy: the owner re-runs the install step to restore the previous one.

Order: (1) new test file with S3 to S11, U1 to U4 red; (2) shim change, green; (3) mutants seen; (4) pre-push (bin/cloud-prepush) and CI; (5) held for the owner.

Risks: R1 a refusal of a graphql body mutation breaks a lane that uses it (grep found none; the line names the REST alternative). R2 reading the --input file or stdin consumes stdin once: the signed text is passed to the real gh as stdin or a temp file, as the -F @- path does today. R3 a large --input file: read whole, bounded by what gh itself accepts; an unreadable one is refused. R4 a JSON body already holding a marker is signed once (the same rule as the existing sign()). R5 --input on a non-comment endpoint (issues/1 PATCH, labels, merge) is not touched (U2, U3). R6 the shim gets longer; the cost is stated, not hidden.
