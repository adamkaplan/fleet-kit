## Constraints

- PC-1: The existing pinned rows of `test_guard.py` and `test_cw_gh.py` do not change; only rows are added.
- PC-2: The shell guard and the client read the ONE table, and the guard-vs-client agreement test is the proof they agree.
- PC-3: No new token permission is taken by this ask beyond the clause on the token; the worker's token set stays one table.
- PC-4: Credentials-class path: held for the owner; the guard is a convenience, the token's scope and the repository's rules are the boundary.

## Open choices (one recommendation each)

1. **Where the table lives.** Recommend one file `cloud/worker/guard-table.tsv` (columns: id, allowed|denied, tool, verb or method, path pattern, exact refusal text). Both programs read it at run time; the `opencode-worker.json` patterns are generated from or checked against it. A test runs every row through the guard and through the client and fails on any difference. Alternative: a table inside the client, rejected because the shell guard must stay shell only and cannot import it.
2. **Build order.** As above; the first ask creates the file and the test, the others only append rows.
3. **Denied-form strings.** One line `refused: <row id>: <fixed phrase>: the repository's rules are the guard; this wrapper is only a convenience`, as the guard prints today; no argument value is ever printed; exit status 3, before any network call.
4. **Token.** No new token permission is requested by this ask except as stated in the clause on the token; the token already holds pull requests write.
5. **Held.** The worker's shell guard and token paths are credentials-class: the pull request is HELD for the owner. The impact floor expects the owner's approval, never delegated, a mutant for each denied row, and the image rebuild on the Chief of Staff's word.
