## Cause (clause 1)

The pod's git token is a one-hour, one-repository installation token, minted at launch and held as the git-token key of the per-run Secret; the pod's credential helper reads the projected file at each call. The reaper renews it by the same mint route (30 minutes left), but a reaper that sleeps, a refused vault or a late kubelet projection leaves the file expired. The stop path then runs cw-end-hook (and cw-prestop), whose push is refused, and the work is lost when the pod ends. Reading the code today: no minute-40 note exists in cloud/launcher or cloud/worker (grep finds none), so the note is new text, not an edit.

## Open choices (one recommendation each)

- (a) Who asks for the fresh token. The pod holds no credential for the minter and must not (the minter credential is long-lived and stays on the operator side). What exists today: the launcher's mint route (run_git_token_cmd) and the reaper's renew step that patches the Secret, which the kubelet projects into the pod within a minute or two. What is missing: a renew on the stop path itself, before the hook runs, and a wait for the projection. Recommendation (i): the stop side mints through the same route, replaces only the git-token key, then runs the hook; the hook, on an ended-token refusal, signals the stop side through its result for one refresh and one retry. Not (ii) a request through the hub: it would give the pod a path to a credential. Cost: the stop waits for a mint of up to a minute plus the projection delay; the stop is slower only when the token ended.
- (b) The minute-40 note names the branch <worker>/wip and the exact command: git push origin HEAD:refs/heads/<worker>/wip (plain, never forced). Timing test with a fake clock: no note at 39:59, one note at 40:00, never twice. Cost: one more line in the pod's input.
- (c) Scope: same repository, same permissions, same one-hour cap (the existing 61-minute refusal), never wider; the token never printed or written to a log, record or audit; the pod's token file is replaced by temp file and rename in the same directory.
- (d) Exactly one refresh and one retry. A refused refresh means no second attempt and no loop. A push refused for another reason (rejected ref, hostile configuration, network) triggers no refresh. Cost: a second token end during the retry loses the work, stated in the documents.
- (e) The stop's audit line and run record say refresh: used, refused or none (a word, never a value).

## Out of scope

The reaper's own renewal schedule, the minter's manifest, the guard and permission files, the model credential, a longer token life.
