# Plan for #1477: a pod's relay call is answered inside the hub's wait

plan-format: 2
size: M

Canonical issue: https://github.com/adamkaplan/fleet-kit/issues/1477

Intent: A pod's relay call (prove, verdict, gates, report) is answered by the Mac daemon within the hub's 30 s wait, not by a later replay.

## Facts read

- `bin/fleet-switchboard` `run_daemon` runs `engine.run_pass()` and then `cloud_relay_daemon.pass_if_configured(...)` inline, once per loop. The relay is therefore pulled only after the engine pass ends, then the loop waits up to `next_poll(engine, poll)` (poll default 5 s, `poll_seconds`).
- The hub (`bin/cloud_relay.py`) waits `WAIT = 30.0` s for the daemon's answer. An engine pass longer than that (S13 live proof) leaves the pod's call a 504 "replay with the same call_id", while the daemon records it minutes later.
- `bin/cloud_relay_daemon.py` bounds: `READ_DEADLINE` 30 s per hub request, `PASS_BUDGET` 60 s per relay pass, one hub worker thread at a time, up to 40 GitHub context reads per pass with no deadline of their own, head read outside the ledger flock under `HEAD_TIMEOUT` 10 s.
- `docs/cloud-channel.md` "Relay timing assumption" says the pass interval must be shorter than the hub wait; that holds only if the pass itself is short, which it is not.

## Done-when

Joined, the clauses below are the issue's Done-when, split at its own separators:

```yaml
clauses:
  DW-1: with the daemon running normally, 20 relay calls from a pod in a row each return 200 or a named refusal within 30 s
  DW-2: and a test with a daemon pass longer than the hub wait shows the relay served on its own short loop.
```

(1) with the daemon running normally, 20 relay calls from a pod in a row each return 200 or a named refusal within 30 s,
(2) and a test with a daemon pass longer than the hub wait shows the relay served on its own short loop.

## Outcome wanted

Relay requests are pulled and answered on their own short cadence (well under 30 s, target 5 s or less between pending checks), independent of how long the engine pass takes. The engine pass and the relay each stay bounded; neither can stall the other. The result of every local command, the ledger flock and the per-pass GitHub reads are unchanged.

## Constraints

- PC-1: Exactly-once records and the refusal texts do not change: the same call_id is replay-safe and the report stays at-most-once (claimed, delivered, done). Reason: pods and the hub rely on it.
- PC-2: Local commands and the engine pass are unchanged in result and audit lines; with no relay configured nothing new runs. Reason: the owner's daemon must not change for people not using the cloud.
- PC-3: The ledger flock and the per-pass GitHub reads stay as they are (head outside the flock, no network under it). The relay loop must take the same lock, so there is no second writer. Reason: the issue says so and the ledger is the single source.
- PC-4: Daemon cannot be stalled by the relay: the total deadline (`READ_DEADLINE`), one in-flight hub worker, `PASS_BUDGET` and the audit lines are kept; a stuck request is cut, not waited for. Reason: the owner's daemon must never hang.
- PC-5: The hub (`bin/cloud_relay.py`, the cloud hub) is not changed unless unavoidable; `WAIT` stays 30 s.

PC-4 and PC-5 are covered by S3, S4 and by review of the diff (no hub file in the changed list).

## Out of scope

- Changing the hub's wait, queue or 504 text; making the engine pass shorter; adding a deadline to the 40 GitHub context reads.
- Push-style notification from hub to daemon (a later option).

## Areas touched

- `bin/fleet-switchboard` (`run_daemon`: start and stop the relay loop; a held-PR area, bin/).
- `bin/cloud_relay_daemon.py` (a loop entry with its own cadence and budget; held area).
- Tests: `bin/test-cloud-relay-daemon` (new scenarios S1 to S4, U1 to U4 there or in a new test file beside it).
- `docs/cloud-channel.md` ("Relay timing assumption": now the relay has its own cadence, not tied to the engine pass).
- `bin/` is a held-PR area: the pull request needs the owner-held review path.

## Mutants to name in the tests

1. Relay still called inline after `run_pass` (S1, S2 fail).
2. Relay loop joined or waited on from the engine pass (S3 fails).
3. A new thread per tick, no single in-flight worker (S4 fails).
4. Total deadline or PASS_BUDGET removed (S4 fails: a stuck request never cut).
5. Relay loop skips the flock or reads the head under it (U4 fails).
6. Relay loop started with no hub configured (U3 fails).
7. Cadence longer than 30 s (S1 fails).
8. A refusal reworded, or a replay writes a second record (U2, U1 fail).

## Risks and rollback

- Risk: two threads write to the ledger at once; kept safe by the same flock (PC-3), tested in U4.
- Risk: the relay thread outlives the daemon on stop; the loop checks a stop flag and the thread is a daemon thread, joined with a short bound.
- Risk: more hub polling load; at most one request per cadence tick, under the same budget.
- Rollback: revert the one pull request; the inline call returns and behaviour is as today (504 on a long pass, replay-safe).

## Open questions

- Cadence value: 5 s (the existing poll) or 2 s? Proposal: 5 s, the same as `poll_seconds`, kept as its own setting.
- Thread in the same process or a separate process? Proposal: a thread in the same process, so the single-instance lock and audit stay one.
- Does the live tester need a deliberately slow pass? Proposal: use the real pass during a busy period, or a test-only fake delay env var that is off by default.
