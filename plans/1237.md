### Cause (clause 1, stated first)
`ci-record` does not read the check-runs itself. `ci_record_core` (`bin/fleet-switchboard`, about line 24574) takes `ci = (ctx.facts or {}).get("ci")` and refuses with `"CI is %s at %s (only a complete, green run is recorded)"` (about line 24596) when it is not "green". That value is `pr_ci_of(data.get("statusCheckRollup"))` (about lines 11608 and 11881), the same value the merge gate's CI read uses. `pr_ci_of` gathers every entry of the head's rollup, passes it through `ci_runs.newest` (`bin/ci_runs.py`), and answers failing if any kept entry is CANCELLED, FAILURE and so on. `newest` groups by `_identity`: the pair (workflow name, check name). So only a re-run of the SAME check name supersedes an older run. Shape, with neutral numbers: workflow W, run A (attempt 1) is cancelled and left checks named `plan`, `matrix.name`, `matrix.cloud`; run B (attempt 2) is green and has different check names. Each of A's names is a group of one run, so the cancelled entry is its own newest and the head reads failing for ever, though the latest run of W is green. Recorded: pull request heads whose real checks were green on a second attempt were refused with the text above; the placeholder checks of a merged pull request earlier did the same. `item-ci-record` reads check-runs through `iv.ci_decision`, a separate path (see Risks).

### Approach (what, not how)
Group the head's check-runs by WORKFLOW RUN: for each workflow only the newest run by creation counts, and every check of an older run of that workflow is ignored whatever its name. The latest run of a workflow that is not complete and green (cancelled, failed, queued, running) makes the head not green, as today. A head with no run of a required workflow, or whose latest run is not complete, is refused with the workflow and run named. One function does this reading and both `ci-record` and the merge gate call it, so they cannot disagree. Status contexts (no workflow) keep today's by-name rule. No new GitHub write.
