### Cause (clause 1, stated first)
The alert is `unowned_line` (`bin/red_ci.py`, "... and no worker owns that pull request"), sent from `red_ci_runs` (`bin/switchboard/alert_labels.py`, about line 221) through `red_ci_tell`. Three faults make an old head re-fire:
1. The key is `"pr-unowned:%s#%d:%s:%s:%s" % (repo, number, head, run["id"], attempt)` (about line 259): it holds the head, but also the run id and the attempt. So every re-run, and every other run (another workflow) at the same head, is a new key and is told again. The intent is a key of (PR, head, check) only.
2. "Current head" is guessed from the runs of the catch-up read: `current[number]` is the head of the newest run in that read (about lines 234-240), not the head the pull request has now. When a pull request's newer runs are outside the read, an old head is the newest seen and passes the `current.get(number, (0, head))[1] != head` test. No read of the pull request's present head or state is made.
3. No state check: a run record keeps its `pull_requests` list after the pull request is closed or merged, so a closed or merged PR still alerts. Also the memory is bounded (`red_ci_save` keeps the last `ALERT_MEMORY_MAX` keys), so an evicted key is told again; with the key of 1 growing per run this makes the repeats ("about a dozen times" each, #1304 at an old head since 18:49Z) worse. The record is persisted in `red-ci.json`, so a restart alone is not the cause.
This is the daemon's delivery path (the Chief of Staff alert); the daemon file is not edited if the change can stay in `bin/switchboard/alert_labels.py` and `bin/red_ci.py`.

### Approach (what, not how)
Key the unowned alert by (repo, PR, head, check name) only. Before telling, decide from the pull request's present facts (head sha and state, read once per PR per pass, or from the data already read when it holds them) that the PR is open and the run's head equals its head; if the facts cannot be read, say nothing (never tell on a guess). A new head is a new key and alerts once. Keep the key memory long enough that an unowned alert of a live PR is not evicted by run-keyed churn.

### Done when (copied exactly from the ask)
Done when: (1) the cause is stated first from the alert code and the recorded cases (which key the alert dedups on, and why an old head re-fires); (2) the alert is delivered ONCE per (pull request, head, check): a second pass at the same head sends nothing, across a daemon restart; (3) never for a head that is no longer the pull request's current head, never for a closed or merged pull request; (4) a NEW head with a failing check alerts once again; (5) tests with the recorded shapes (the stale head of #1304, a closed pull request, a new head) and mutants (a key without the head; no state check), and the docs say it.
