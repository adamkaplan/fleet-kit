### Cause (clause 1, stated first)
Today the orders are a conversation message. `OrdersFacts.cos_fact` in `bin/fleet-switchboard` (about line 31109) builds the fact with key `orders:cos:<hash8>:<compaction id|start>`, and `orders_note` (line 3657) renders it as a note sent into the session. The fact is pending only while that key is absent from the transcript or inbox. So the orders are a message in the very conversation that a compaction summarises: when the summary is written, the note is summarised with it, and a rule the summary does not keep is gone from the model's context. That is the structural cause and it needs no failed delivery.
The delivery after a compaction can also fail to run, in three places: `v2_light` turns the compaction read off (`V2_LIGHT_OFF`, line 3774, "compactions (orders after one)"; `compaction_page` returns nothing, about line 4223); `compaction_page` remembers its list for up to `COMPACTION_TTL_MAX` = 30 s (lines 3934, 4365); and `completed_compaction` (line 31034) sees only a completed compaction, so the key stays "already delivered" until one is. The text itself is not cut here: `read_cos_orders` (line 31464) refuses over 8192 bytes with `CosOrdersError`, and `cos_orders_text_of` strips only comments (a refusal is audited as `orders.unreadable`).
`plugins/fleet-hooks/index.js` has no system-prompt hook and no role check: `wireEvents` only pushes the `compaction` event to the daemon. Which of the cases happened in the recorded case is decided from the audit line `orders.unreadable`, the sent-key ledger and `v2_light` in the config at that time; the work item shows it in the pull request, and if the audit cannot tell, it says so.

### Approach (what, not how)
The orders travel in the model's system prompt, outside the conversation, through a plugin hook that runs on every model call, only for the agent whose role is the Chief of Staff. The text is the file's, word for word after the template's comment strip; a file over 8 KB is refused with a visible note and never cut. A compaction cannot remove a system prompt, and an edit shows on the next call. The conversation note stays only where the hook cannot be used (reason stated in the docs), re-sent in full after each compaction and at each change, with `v2_light` not turning that off for orders.

### Out of scope
The judge's reading of the file; the guard on writing the file; the 8 KB cap; charter orders to other agents; any change to the compaction itself or its summary; a new GitHub call; editing the owner's orders file.

### Areas touched
`plugins/fleet-hooks/index.js` and its test (a held-PR area), the orders delivery in `bin/fleet-switchboard` (a held-PR area: the daemon file), `templates/` only if the file's header wording changes (held), `docs/switchboard.md`, tests. The pull request holds for the owner if the floor says so (a plugin file is a top-tier path).

### Risks and rollback
Risk: the plugin hook name or its role check is unverified in the running service (the plugin file itself says its hook names are unverified); a role wrongly read would give orders to a worker, which scenario S4 pins. Risk: orders both in the prompt and in a note (double text); the note is stopped when the hook is live. Rollback: revert the pull request; the file and the registry are untouched.

### Integration branch
Stay on main.
