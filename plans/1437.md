### Cause (clause 1, stated first)
The fact is made by `intent_change_fact` (`bin/fleet-switchboard`, about line 14833). It returns None unless `intent_diff(payload)` finds a change in the Intent section, and its key is `intent.edit:<repo>#<issue>:<updated_at>`. The key is the issue and the issue's `updated_at`; it holds no body hash and no edit identity. The source keeps the edit in `GitHubSource.intent_edits` (about line 11281, filled in `note_issue_edit` about line 11517) and drops it only in `acknowledge` (about line 11484), which the engine calls when it finds the key delivered (`_plan_pending`, about line 2912, and after a write, about line 3034). `intent_edit_facts` (about line 11564, called from the fact list about line 11673) rebuilds a fresh `Fact` for every Chief of Staff on EVERY wake while the payload is still held. So an edit is delivered again whenever the engine does not find its key as delivered: the check reads only the newest `READ_LIMIT` (200) transcript messages from `since` (`delivered_keys`, about line 2824), a result that is `complete=False` or a transcript that has moved on loses the key, and the held payload then yields the same fact again. Nothing remembers per recipient that the edit was told. `intent_verdicts` (about line 11280) only memoises the wake decision, is memory only and is cleared past `GITHUB_QUEUE_LIMIT`; `intent_edits` is also memory only, so a restart forgets both. The recorded case (one edit, ten deliveries) must be reproduced in the work item with the real payloads before the fix: which of these paths re-made the fact is a finding of the work, stated first in the pull request.

### Approach (what, not how)
A delivered Intent edit is recorded durably per recipient, under a key that names the edit: issue (with repo), edit time and a hash of the Intent text. The fact source stops offering an edit already recorded for that recipient, whatever the transcript window shows, and the record is written where the delivery is confirmed (the `_acknowledge` path) and read back at start. A second real edit changes the time and the hash, so it is a new key and is delivered once. The record is bounded in size and age.

### Dependency and the `send` ask
This ask is independent of `send --file`. The dedupe changes no text path: `cmd_send` (`_cmd_send`, line 13622 onward) takes its text from the words (`" ".join(args.text)`) and the 4,000-character `MESSAGE_CAP` applies in `compose`. #1355's text-file form (PR #1393, branch `origin/c1355`, `read_text_file`, `TEXT_FILE_MAX = 100000`, on top of #1315's `finding_parts`/`compose` in `origin/c1302`) covers `remind` ONLY, not `send`. A `send --file` ask would be a separate plan after #1315 and #1355 land and would reuse the one function `reminders.read_text_file`. It is not part of this plan.

### Done when (copied exactly from the ask)
Done when: (1) the cause is found and stated first from the code and the recorded case (one edit of an issue body, confirmed once in GitHub's edit history, was delivered about ten times as "The Intent section was edited", riding later wakes): where the `intent.edit` fact is made, what identifies it (issue, edit time, body hash) and why the same edit is made or delivered again; (2) a given edit is delivered at most once per recipient, however many wakes follow, and a second real edit is delivered once; (3) the dedupe survives a daemon restart; (4) tests with mutants (no dedupe; dedupe by issue only, which drops a second real edit) and the documentation says it.

### Work item 1: an Intent edit is told once per recipient
Done when: as above, clauses (1) to (4).

### Out of scope
`send` and `remind` text handling; the wake decision (`intent_edit_wakes`); other fact kinds; new GitHub writes; the webhook forwarder.

### Areas touched
`GitHubSource` and `intent_change_fact` in `bin/fleet-switchboard` (the daemon file, a held-PR area), a small state file under the state directory, `docs/switchboard.md`, `bin/test-switchboard`. Not touched: templates/, shims/, plugins/fleet-hooks.

### Risks and rollback
Risk: a dedupe by issue alone would drop a second real edit (S4 pins it); a record that is lost on restart repeats an edit once (S5). An unreadable or corrupt state file is treated as empty and says so in the audit, never raises. Rollback: revert the pull request; the state file is ignored.

Stay on main.
