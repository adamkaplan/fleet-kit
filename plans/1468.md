### Cause (clause 1, stated first)
The reminder fact is built in `ReminderFacts` (`bin/switchboard/reminders.py`, about line 449): `Fact("reminder:" + item["id"], item["to"], "reminder", text, item["at"], ..., sender=item.get("from"))`. Its only treatment of lateness is the text note "(late by N min)" added when `late >= LATE_NOTE_SECONDS`, a suffix on the body, not a first line "delayed: sent HH:MMZ". Each due item is made by `add_reminder` (line 77) and is its own fact with its own id key, so a copy is never the same key as another copy. Delivery then runs `merge_wake_facts(plan.recipient, plan.pending)` (line 241 of reminders.py, called in the engine delivery near line 2961 of `bin/fleet-switchboard`). That function merges only facts whose class is in `WAKE_KINDS = ("sweep", "triage")` (line 218; `wake_class_of`, line 235, reads `fact.kind` or `wake_class`): the kind "reminder" is in neither, so it passes through untouched, one fact per turn. `delayed_since` is not defined in this checkout (#1402 has not landed here): it names no reminder by design, it is for alerts and digests. Covered already: #1285 (a newer copy of the same owner and key drops a fired copy: needs a key), #1401 (a cancelled chain and a superseded copy on its way), #1402 (sent time, "delayed" mark and replace rule for alerts and digests only). Left open: an unkeyed reminder (no key, so #1285 never applies) and a keyed one that is not superseded (no newer copy exists). Recorded: about thirty fired copies queued and delivered hours late, one per turn, about thirty turns in a day.

How `send` takes its text: `cmd_send` (line 13622, bounded by `run_bounded`) calls `_cmd_send` (line 13686), which reads `send.add_argument("text", nargs="+")` (line 21444), joins `text = " ".join(args.text).strip()`, refuses an empty one ("nothing to send"), and calls `engine.send(sender, name, text, ...)` (line 3277). There is no length refusal on the command line: the cap `MESSAGE_CAP = 4000` (line 1848) applies only at delivery, where `compose` cuts a newer send and the delivery path reports "[cut at 4000 characters]" (line 2965).

### Approach (what, not how)
1. Delayed mark: a reminder copy that fired more than 30 minutes before its delivery begins with the line "delayed: sent HH:MMZ" (UTC); within 30 minutes it is unchanged (and no "(late by N min)" suffix is added on top: the mark replaces it).
2. Merge: queued reminder copies with the same sender, recipient and text become ONE line with the count and the newest sent time, keyed or not; every merged copy is acknowledged (as `merge_wake_facts` carries its member keys) so none is delivered again. Another sender, recipient or text is never merged. The merge uses the sender, recipient and exact text as its identity, not the key.
3. `send --file` (the dependency below): the text of a send comes from a file in parts.

#1355's text-file part form (PR #1393, branch origin/c1355, on top of #1315's `finding_parts` and `compose` in origin/c1302): it covers `remind` ONLY (`remind --text-file`, `read_text_file` in reminders.py, `TEXT_FILE_MAX = 100000`, `TEXT_CAP = 4000`, text over the cap refused on the command line with the hint to use `--text-file`). It does NOT cover `send`. This ask reuses ONE shared function: `read_text_file(path)` (returns text or a refusal reason), and carries the parts through the same `finding_parts`/`compose` path. No second reader and no second splitter is written. File rules: a regular file (not a symlink pointing out of the user's directories), at most 100 KB, readable, UTF-8, not empty.

For `send`: `--file F` (not with words); parts are sent in order, each under the cap, with a header "part i of n" when there is more than one part; a text under the cap is one part with no header; a command-line text over `MESSAGE_CAP` is refused with the hint to use `--file`; a failing part is named and no later part is sent.

Dependency: this ask builds AFTER #1315 (finding_parts/compose) and #1355 (read_text_file, `--text-file`) land; the reminder items (1 to 3) are independent of them, `send --file` is not.
