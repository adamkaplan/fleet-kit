### Cause (clause 1, stated first)
`ci_record_pass` in `bin/fleet-switchboard` spends ONE budget (`pass_seconds` 10, `calls_per_pass` 30) in this order: first it re-reads the open-PR list of every stale repo (2 pages each, `read_pages(..., cap=2)`, stale after `CI_RECORD_LIST_TTL` 180 s), and only then visits PRs, each charged `CI_RECORD_PR_COST` 4, oldest-checked first. With four repositories in `plan_gates.repos` the lists alone take up to 8 of the 30 calls and most of the 10 seconds when GitHub is slow, so the PR loop's `break` (`budget[0] < CI_RECORD_PR_COST or time spent`) leaves PRs unvisited. That `break` writes NOTHING: a skipped PR leaves no audit line, and `ci_record_core(..., quiet=True)` also writes nothing for `not-green`. This is the silent skip the ask names. Hypotheses, as found in the code:
- H1 (budget spent on list re-reads before any PR): TRUE by the code order above; the tester confirms it on the audit of one case (a pass at the time CI turned green with no `gate.ci_record` line for that PR).
- H2 (unreadable retry doubles): TRUE. The `except` branch sets `delay = min(1800, 300 * 2 ** (fails-1))`: a PR whose `gh pr view` failed once (the audit shows 'socket is not connected', 'connection reset by peer') waits 5 minutes, and after more failures up to 30, with no regard to whether CI has just turned green. A network blip is not a PR fault.
- H3 (head moved while pending): PARTLY TRUE. When `got["head"] != listed_head` the retry is `list read time + 180`, so a push waits for the next list refresh, and that refresh is itself behind the budget order of H1.
- H4 (restart empties memory; `recorded: 0` is not proof): TRUE as a reading rule. `CiRecordState.recorded` and `last_record` are per process; the counter counts only what THIS process wrote, so a manual `gates ci-record` first leaves `already` and `recorded` stays 0. The status line must show `already`; it is not a failure.
- H5 (PLAN link in another form): TRUE for a narrow case. `PLAN_LINK_RE` is `(?m)^\s*PLAN:\s*(\S+)`: a body with `**PLAN:**`, `Plan:` or the link after other text on the line is never considered, and the skip is silent. The tester checks the four recorded bodies.
- Not in the code to blame: a plan hash revised after approval gives `no-plan` or a new hash, so the verdicts are written again only when the pass visits the PR (retry `CI_RECORD_FAILED_RETRY` 180 s); a base branch is not read anywhere in `ci_record_pass` (the list is `state=open`, any base), so that candidate is EXCLUDED for the pass and the tester shows it from the integration case's audit; the macOS leg finishing last is covered by `pr_ci_of` (a pending check gives `pending`, retried after 60 s), so it only delays by up to one minute plus the budget.
Smallest root fix: visit PRs BEFORE list re-reads (or reserve a share of the budget for PRs), retry an unreadable PR at the next pass first (the doubling only after repeated failures), and audit every skip with its reason.
The G6 half: in `bin/plan_ledger.py` gate G6 the `facts["captain"]` branch returns `waiting` ("held for the owner (MERGE: captain)") even when the floor read says not held.

### Approach (what, not how)
The pass gives PRs a guaranteed share of every pass, and a list is re-read only with what is left. A PR that was skipped (budget, unreadable, still running, no plan link) is looked at first on the next pass, and each skip is one audit line with its reason (deduplicated per PR and reason). An unreadable read retries at the next pass, then backs off only after several failures in a row. G6 says "a marker without a hold: set `MERGE: automatic`" when the floor says not held and line 1 reads `MERGE: captain`.

### Done when (copied exactly from the ask)
Done when: (1) the cause is found and stated first, from the recorded cases (four pull requests in one day where the verdicts were still missing after CI was green and the lane or the orchestrator had to run `gates ci-record` by hand: an integration pull request after its proofs were redone at a new plan hash, a tools-only pull request, a decomposition pull request, and one in another repository): which of these it is, shown from the audit and the daemon's own pass (a plan hash revised after approval, the macOS leg finishing last, the per-pass read budget skipping the pull request, the pass recording only after a proof exists, a pull request whose base is not the default branch, or something else); each candidate is excluded or confirmed by the audit lines of one case; (2) the daemon records the `ci` verdicts within one pass of the last required check finishing green, for a pull request of any base branch and of any repository listed under `plan_gates.repos`; (3) a pull request skipped by a pass (budget, unreadable, still running) is retried on the next pass and the skip is audited with its reason, never silent; (4) when the floor says a pull request is not held but its description's first line reads `MERGE: captain`, gate G6 says so plainly (a marker without a hold: set `MERGE: automatic`), and not `waiting`; (5) tests: a fixture of each cause found; a fixture where the last check finishes after the proofs; a fixture of a skipped pass retried; a mutant that records before the check is green, one that never retries and one that leaves G6 as `waiting` fail; (6) the documentation states when verdicts are recorded and what a skip means.

### Out of scope
Changing what a `ci` verdict means; any GitHub write; the label pass and triage budgets; changing `plan_gates` configuration of the live daemon (a separate step); a webhook-driven recorder.

### Areas touched
`ci_record_pass` and `CiRecordState` in `bin/fleet-switchboard` (HELD AREA: the daemon file), gate G6 in `bin/plan_ledger.py`, `docs/switchboard.md`, tests. No matrix, templates, shims or plugins change. The floor decides whether the pull request is held.

### Risks and rollback
Risk: PRs first, lists second, means a new PR is seen one pass later, and a retry at every pass can add calls on a broken network. Both stay inside `calls_per_pass`, and the backoff after repeated failures bounds the second. Rollback: revert the pull request; the verdicts written are ordinary ledger entries.
