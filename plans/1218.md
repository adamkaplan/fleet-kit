### Cause (clause 1, stated first)
In `cmd_charter` (`bin/fleet-switchboard`, the `pre` block about line 28552 and `guard` about line 28579) the GitHub reads are `parent = engine.intents.parent(value, repo0)` and `root = engine.intents.parent(parent, repo0) if parent is not None else None`. The guard then refuses with `if pre["parent"] is None or pre["root"] is not None: return ("not a sub-issue", "#%d is not a sub-issue of the repository's root issue")`. So it demands that the issue HAS a parent and that this parent has none: it accepts only an ask (an issue under a charter) and refuses every real charter, which has no parent (the parent read answers "No parent issue found" -> None). Recorded: the charters of the kit's own lane and of three product lanes were each refused with that text. The same file treats the shapes the other way round: `ask_of` (about line 20651) says an issue whose parent has no parent is under the charter, and a charter is the issue with no parent; `orchestrator_label()` (about line 16989) is `<user>:orchestrator`, the marker of a charter. Shapes, with neutral numbers: charter #10 has no parent and carries the label; ask #11 has parent #10. The guard never reads the label at all.

### Approach (what, not how)
A charter is judged by what it is: an issue with NO parent that carries the fleet's own orchestrator label. An issue with a parent is refused as "is an ask, not a charter"; an issue with no parent and no label is refused as not a charter; a parent read that fails (an error that is not the "no parent" answer) is refused as unverified and never accepted. The reads stay before the registry lock, bound to the issue number and repo, as today. No change to the clear machinery.
