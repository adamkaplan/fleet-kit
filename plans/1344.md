### Cause (clause 1, stated first)
In `cmd_review_post` (`bin/fleet-switchboard`, about line 23202) the verdict table `REVIEW_POST_VERDICTS` (about line 23107) maps `approve` and `request-changes` to the Reviews-API events APPROVE and REQUEST_CHANGES. The body is posted by `_review_api(... "POST" ...)` (about line 23148), which returns `(ok, parsed, why)` with `why` cut to one line of 200 characters. The own-account case is only handled after the fact: about line 23234, `REVIEW_OWN_REFUSAL` (about line 23109) is matched against `why` and, on a match, the post is retried as COMMENT. The code never compares the pull request's author with the poster's account before posting, so it cannot say why or what to do in advance; any refusal whose text the pattern does not match ends in `GitHub refused the review: <why>`, and the reader saw only "GitHub refused". Nothing reads the reviews already posted at the head, so nothing stops a second review by the same reader at one head: the recorded case is about 40 one-line comment reviews at one head and 24 at another, posted to find the cause. Shapes, with neutral numbers: pull request #20 authored by account A, poster is account A, verdict approve: refused by GitHub with "can not approve your own pull request".

Context of the tightening (a merged follow-up, the charter set guard): the batch readers found that 3 of 12 mutants survive in the `charter set` tests, because the rig's fakes ignore the repo argument of `IntentReader.parent(` and `IntentReader.issue(`, and the label read goes through the ttl cache `IntentReader._cached` (about line 18845), so a stale label can be served. This plan makes the same kind of rig honest for the new reads: the fake takes and checks the repo, and the author and reviews reads of `review post` are not served from a cache.

### Approach (what, not how)
Before posting, read the pull request's author and the reviews already posted at this head by this reader's marker. A second review by the same reader at the same head is refused, naming the earlier review, unless `--again` is given. When the author equals the poster's account and the verdict is approve or request-changes, post a COMMENT review whose first line is `Review of <head>: <WORD>` with the verdict word, and say so in the output. When GitHub still refuses, print GitHub's own reason as one capped line and the next step: "this pull request is authored by your own account: post with `--verdict comment`; keep the first line `Review of <head>: APPROVE`". A review by another account is posted as today.

### Risks and rollback
Risk: a wrong author read posts a comment where an approve was possible; an unreadable author falls back to today's post-then-retry path, never to a silent drop. Risk: the second-review check blocks a legitimate re-review; `--again` is the answer and the refusal names it. Rollback: revert the pull request; no registry or stored data changes.
