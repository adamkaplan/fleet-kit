## The cause, from the code (DW-1)

Verified on `integration` (3a706c1):

- **Unchanged list: only the mtime moves.** `LocalStore.publish`, bin/fleet-switchboard:12440-12449: when the held file's decisions, errors and provisional flag equal the new ones it runs `os.utime(path, (now, now))` (line 12449) and returns False. The body is not rewritten, so `written_at` (set only at line 12453, `iso(now)`) and `generation` keep the values of the last real change. An idle, healthy daemon therefore shows a `written_at` that grows older without bound while the mtime stays within one pass of now. `written_at` is the time of the last change, not of the last sign of life.
- **Changed list.** Lines 12450-12467 write a temp file, set its mtime to `now` and `os.replace` it: `generation` rises by one, `written_at` and `daemon_pid` (`os.getpid()`) are fresh.
- **Generation seeding.** `engine.decisions_generation` starts at 0 in the engine (line 4417). `publish` sets it to `max(engine value, generation in the held file) + 1`, or `+ 0` when only the provisional flag changed (line 12452). With a held file the count carries on across a restart; with no file (a fresh volume, a new pod) or a file without an integer generation, the first write is generation 1. A restarted cloud daemon thus publishes a LOWER generation than a puller's copy, with a new `daemon_pid`.
- **What the plugin does with mtime.** plugins/fleet-decisions-tui/decisions.mjs: `STALE_MS = 180_000` (line 10, "older than this (by mtime, which every daemon pass refreshes): not current"); `loadSnapshot` takes `ageMs = max(0, now - info.mtimeMs)` (line 161) and returns `status: ageMs > STALE_MS ? "stale" : "ok"` (line 163). The plugin never reads `written_at` or `generation`. So the whole freshness judgment in the cloud rests on the pull setting the local mtime honestly: to now only when the source is live, and otherwise left or aged (`mark_stale`).
- **What PR 1160 did** (`git fetch origin hub/h1078-fresh`, commit 4aa8579 on top of the merged 3d885d7; two files, bin/decisions_pull.py and bin/test-decisions-pull). It (a) made `generation` and `written_at` mandatory (else Garbage); (b) refused a body whose `written_at` is more than `STALE_SECONDS` (180 s) old, aging the held file; (c) refused a body whose `generation` is lower than the held file's, aging the held file. Read against the facts above, it is wrong in three ways: (b) judges liveness by `written_at`, which for an idle healthy daemon is old, so the panel would say "daemon not updating" for a perfectly healthy daemon that merely has nothing new (a false stale); (c) after a restart at generation 1 on a fresh volume every later pull is refused for as long as the puller holds a higher number, so the panel decays to stale permanently, and a single body with a huge generation does the same (nothing bounds it, nothing recovers it); and nothing checks `written_at` against the future, so a clock-skewed body is treated as young. It judged freshness from the body, and the body does not carry freshness.

## Design choice: one liveness value (DW-2)

**Chosen: the source command supplies the file's age** (the mtime-based age of `decisions.json` where the daemon lives, in whole seconds, computed on the source side by its own clock), and the pull accepts it through a second command option (`--age-command`, printing one non-negative integer). No daemon change.

Why this one:
- It is exactly the signal the local panel already uses (the mtime that `publish` refreshes on every pass, plugin line 161), so cloud and local mean the same thing by "fresh", and the plugin's 180 s rule is the single threshold.
- The daemon already writes it on every pass (`os.utime`, line 12449); no new write path, no new body key, and no change to the idle-daemon path of the hot loop. The daemon and its tests stay as they are, which the intent asks for ("the daemon and the plugin mostly unchanged").
- An age (a duration measured on one clock) has no clock-skew problem between the pod and the Mac. The alternative, a `touched_at` epoch written next to the generation, would be compared across two machines' clocks and needs the same future/skew guard again.
- The alternative's costs, for the record: the daemon would stop merely touching the file and rewrite the body on every pass (an atomic write of up to the whole list each pass, a changed `publish` contract and its tests in bin/test-fleet-switchboard, a held-area change to the daemon), and a stopped daemon would still need the puller to read the age from somewhere, so it buys nothing here. Rewriting is M of extra work and risk for no gain; the chosen option is smaller AND adds no new coupling, so the choice is on the result, not on effort.
- Cost of the chosen one: the source command is now two reads (or one command that prints both), so a window exists where the file changes between them. Accepted: the age only decides stale or not, and a stale answer is the safe side. The age may be at most a bound (see PC-2); a missing, non-integer or negative age is treated as "source unreachable" (the held file is aged), never as fresh.

`written_at` is kept only as a plausibility check: a body whose `written_at` is more than a small tolerance (60 s) in the future of the puller's clock is Garbage-like (not written, held file aged); an old `written_at` is NOT a reason to refuse anything.

## Constraints

- PC-1: The pull judges freshness only from the supplied age, never from `written_at`'s age. Why: an idle healthy daemon has an old `written_at` (publish, line 12449).
- PC-2: The supplied age is bounded: an age above the plugin's stale limit (180 s) means the source is stale, so the held file is aged and nothing is written, as for an unreachable source. A negative, non-integer or absurdly large (over one day, 86400 s) age is treated as unreachable. Why: a bound that cannot be fooled into "fresh".
- PC-3: A lower generation is accepted when `daemon_pid` differs from the held file's (a restarted or new daemon). With the same `daemon_pid`, a lower generation is refused (a stale replay) and the held file is aged.
- PC-4: The generation is bounded: an integer in 0 to 2**31 - 1 (not a bool); above that the body is Garbage. A held file whose generation is outside the bound counts as no held generation. Named recovery: `--reset-generation` makes the pull accept any in-bound generation once; deleting `decisions.json` does the same. Both are named in the module docstring and in the stderr line that refuses a lower generation.
- PC-5: The written file keeps the daemon's shape (same keys, indent 1, sorted keys, final newline, mode 0600, atomic) and the mtime is set to now minus the supplied age (never in the future), so the plugin's own `STALE_MS` rule reads the true age. Why: the plugin is unchanged.
- PC-6: The daemon (bin/fleet-switchboard) and the plugin are not changed. Why: see the design choice; they are a held-adjacent area with their own tests.
- PC-7: No key, token or source body is printed or logged; stderr carries the reason only.

## Out of scope

- Any change to `bin/fleet-switchboard` (daemon) or `plugins/fleet-decisions-tui/` (see the design choice).
- The cloud transport, the source command's own credentials, and where the age command runs (a kubectl/Service Bus recipe is the runbook's, not this slice's).
- Merging or rescuing PR 1160: it is not to be merged as it stands; this slice replaces its judgment. Its parts that stay right (mandatory-shape checks, the held file aged on refusal) may be reused by the worker.
- A wire format change for `decisions.json` (no new body key).

## Areas touched

- `bin/decisions_pull.py`: the freshness judgment, the age input, the generation bound and the recovery flag.
- `bin/test-decisions-pull`: the scenarios above as checks, with the mutants of S11.
- `bin/fleet-switchboard`, `DecisionStore.publish` (`LocalStore.publish`, lines 12440-12467): READ ONLY, and it must NOT change. Reason: it already touches the mtime on every unchanged pass (line 12449), which is the liveness the chosen design reads; the generation restart at 1 and the new `daemon_pid` are handled in the puller. If the other design were chosen the daemon would have to write a bounded `touched_at`/age on every pass instead of `os.utime`; that is not done.
- Held-PR area: none touched. PR 1160 (branch hub/h1078-fresh) holds the same two files and is superseded; the worker rebases on integration and does not build on it.

## Risks and rollback

- The two-read source (body and age) can disagree for one pass: the safe side is stale; mitigate by one command printing both where the transport allows.
- A source with no age support: the pull then reports stale (PC-2) rather than guess; the runbook must give the command. Risk accepted: a false stale is visible and cheap, a false fresh is the bug.
- The source's clock is wrong: an age is a duration, so the skew cannot make a stopped daemon look young beyond the pass interval.
- Rollback: revert the one PR; `decisions_pull.py` returns to the merged 3d885d7 behaviour (the plugin and the daemon are untouched, so nothing else moves). A held file written by the new pull is the same shape, so the old pull reads it.
