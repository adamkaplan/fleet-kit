### Cause (clause 1, stated first)
This is a tightening-only follow-up of the merged charter set guard. In `cmd_charter` (`bin/fleet-switchboard`, the read block about line 28707) the two GitHub reads are `parent = engine.intents.parent(value, repo0)` and `root = engine.intents.parent(parent, repo0)`, with `pre = {"key": (value, repo0), ...}`; `guard` (about line 28733) refuses with "unverified" when `pre.get("key") != (value, repo)`. The batch readers found that 3 of 12 mutants survive: the test rig's fakes for `issue(` and `parent(` ignore the repo argument, so dropping `repo0` from either read, or deleting the repository-binding refusal, changes no test result. Second, the reads go through `IntentReader._cached` (about line 20737), which serves a hit while younger than `ttl` (or `live_ttl`), keyed by `("issue", repo, number)` and `("parent", repo, number)`; so the label read in `issue(` (about line 20756) can be stale, and `invalidate(issue, repo)` (about line 20745) exists but `charter set` never calls it. Third, the shapes named by the readers have no test: labelled root with no parent, a pull request carrying the label, label look-alikes, and a 404 whose body is not "no parent" (`parent(` maps any `not_found` reason to None, so the body is never looked at). Neutral numbers: charter #10 (no parent, labelled), ask #11 (parent #10).

### Approach (what, not how)
Pin by tests, and make the label read fresh. Fakes answer a different shape per repository, so a read without the intent repository gets the wrong shape and the test fails. The label read is invalidated before it is made, so a cached answer is never served to a set. Add the missing shape cases. Nothing else in `charter set` changes.

### Done when (copied exactly from the ask)
Done when: (1) a test whose fake answers a different shape per repository asserts that BOTH reads receive the intent repository, and a test that changes the row's repository between the read and the lock is refused; (2) the label read is invalidated before it is made (or the docs say how long it can be stale, with the number); (3) tests for: a labelled root issue with no parent (accepted), an issue that is a pull request carrying the label (refused), label look-alikes (another prefix, no prefix, a different case), and a 404 whose body is not "no parent" (refused as unverified); (4) mutants: dropping the repository from either read, and removing the repository-binding refusal, each fail; (5) nothing else in `charter set` changes.

### Work item 1: pin the reads and the label shapes
One work item: the tests, the invalidation before the label read, and the mutants.
