## The cause, from the code (DW-1)

Verified on `integration` (3a706c1):

- **Unchanged list: only the mtime moves.** `LocalStore.publish`, bin/fleet-switchboard:12440-12449: when the held file's decisions, errors and provisional flag equal the new ones it runs `os.utime(path, (now, now))` (line 12449) and returns False. The body is not rewritten, so `written_at` (set only at line 12453, `iso(now)`) and `generation` keep the values of the last real change. An idle, healthy daemon therefore shows a `written_at` that grows older without bound while the mtime stays within one pass of now. `written_at` is the time of the last change, not of the last sign of life.
- **Changed list.** Lines 12450-12467 write a temp file, set its mtime to `now` and `os.replace` it: `generation` rises by one, `written_at` and `daemon_pid` (`os.getpid()`) are fresh.
- **Generation seeding.** `engine.decisions_generation` starts at 0 in the engine (line 4417). `publish` sets it to `max(engine value, generation in the held file) + 1`, or `+ 0` when only the provisional flag changed (line 12452). With a held file the count carries on across a restart; with no file (a fresh volume, a new pod) or a file without an integer generation, the first write is generation 1. A restarted cloud daemon thus publishes a LOWER generation than a puller's copy, with a new `daemon_pid`.
- **What the plugin does with mtime.** plugins/fleet-decisions-tui/decisions.mjs: `STALE_MS = 180_000` (line 10, "older than this (by mtime, which every daemon pass refreshes): not current"); `loadSnapshot` takes `ageMs = max(0, now - info.mtimeMs)` (line 161) and returns `status: ageMs > STALE_MS ? "stale" : "ok"` (line 163). The plugin never reads `written_at` or `generation`. So the whole freshness judgment in the cloud rests on the pull setting the local mtime honestly: to now only when the source is live, and otherwise left or aged (`mark_stale`).
- **What PR 1160 did** (`git fetch origin hub/h1078-fresh`, commit 4aa8579 on top of the merged 3d885d7; two files, bin/decisions_pull.py and bin/test-decisions-pull). It (a) made `generation` and `written_at` mandatory (else Garbage); (b) refused a body whose `written_at` is more than `STALE_SECONDS` (180 s) old, aging the held file; (c) refused a body whose `generation` is lower than the held file's, aging the held file. Read against the facts above, it is wrong in three ways: (b) judges liveness by `written_at`, which for an idle healthy daemon is old, so the panel would say "daemon not updating" for a perfectly healthy daemon that merely has nothing new (a false stale); (c) after a restart at generation 1 on a fresh volume every later pull is refused for as long as the puller holds a higher number, so the panel decays to stale permanently, and a single body with a huge generation does the same (nothing bounds it, nothing recovers it); and nothing checks `written_at` against the future, so a clock-skewed body is treated as young. It judged freshness from the body, and the body does not carry freshness.

## Why v1 does not work with the hub as built

bin/cloud_hub.py at 0dd39728, `do_GET`: for `/decisions` it checks the bearer header, then does `_read_json(decisions_path, {"decisions": [], "errors": []})` and answers `200` with that body. Two facts follow. (a) The answer carries the body only: no age, and the file's mtime (the only liveness the daemon writes, line 12449) never leaves the hub, so a puller of the hub has no source age to read. (b) An absent file is answered as an EMPTY 200 (the default), so a hub whose daemon never published, or lost its volume, looks like a healthy empty list. Only a read or parse error gives 503 (`decisions unreadable`). The v1 `--age-command` would need a second read racing the first and still could not see the hub's mtime.

## Design choice: one liveness value, served by the hub (DW-2)

**Chosen: the SOURCE is the hub, and the hub's `GET /decisions` returns the body AND the age.** The response is the decisions body plus one extra top-level field, `age_seconds`: an integer, whole seconds, computed by the hub as `max(0, int(now - os.stat(decisions_path).st_mtime))` on the HUB's clock, read from `os.stat` and never from the file's own content (`written_at` and `generation` play no part). When the file is absent or unreadable (stat or read or parse fails, or the body is not an object) the hub answers `503` with no body, never an empty 200. The bearer check is unchanged: an unauthenticated request is still `401`.

The pull reads body and age from ONE response (one command or one HTTP read; no second command that can race the first), takes `age_seconds` out of the body before writing, and judges freshness from it alone. The written file keeps the daemon's shape (no `age_seconds` key in it).

Why this one:
- It is the signal the local panel already uses (the mtime `publish` refreshes on every pass, plugin line 161), so cloud and local mean the same by "fresh"; the plugin's 180 s rule is the single threshold.
- An age is a duration on one clock (the hub's), so no skew between hub and Mac; the stat-and-body come from one request, so no race.
- The daemon (bin/fleet-switchboard) and the plugin stay unchanged. The cost is a small hub change (see Areas touched).
- Rejected: a daemon-written `touched_at` (cross-clock compare and a rewrite of the body every pass) and v1's second age command (cannot see the hub's mtime, races the body read).

**The old `--age-command` stays only for a source that is a plain file** (a local path or a command that cats a file, with no hub): the age then comes from the second command, as in v1, and is documented and tested as such (S17). When the response is a hub response with `age_seconds`, `--age-command` is not used; if both are given, the in-response age wins and the stderr line says so.

`written_at` is kept only as a plausibility check: a body whose `written_at` is more than 60 s in the future of the puller's clock is Garbage-like (not written, held file aged); an old `written_at` is NOT a reason to refuse anything.

## Constraints

- PC-1: The pull judges freshness only from the supplied age, never from `written_at`'s age. Why: an idle healthy daemon has an old `written_at` (publish, line 12449).
- PC-2: The supplied age (from `age_seconds` in the one response, or from `--age-command` for a plain-file source) is bounded: an age above the plugin's stale limit (180 s) means the source is stale, so the held file is aged and nothing is written, as for an unreachable source. A negative, non-integer or absurdly large (over one day, 86400 s) age is treated as unreachable. Why: a bound that cannot be fooled into "fresh".
- PC-3: A lower generation is accepted when `daemon_pid` differs from the held file's (a restarted or new daemon). With the same `daemon_pid`, a lower generation is refused (a stale replay) and the held file is aged.
- PC-4: The generation is bounded: an integer in 0 to 2**31 - 1 (not a bool); above that the body is Garbage. A held file whose generation is outside the bound counts as no held generation. Named recovery: `--reset-generation` makes the pull accept any in-bound generation once; deleting `decisions.json` does the same. Both are named in the module docstring and in the stderr line that refuses a lower generation.
- PC-5: The written file keeps the daemon's shape (same keys, indent 1, sorted keys, final newline, mode 0600, atomic) and the mtime is set to now minus the supplied age (never in the future), so the plugin's own `STALE_MS` rule reads the true age. Why: the plugin is unchanged.
- PC-6: The daemon (bin/fleet-switchboard) and the plugin are not changed. Why: see the design choice; they are a held-adjacent area with their own tests.
- PC-8: The hub's `age_seconds` is an integer computed from `os.stat` mtime on the hub's clock, never from the file's content, never negative.
- PC-9: The hub answers `503` (not a 200) when the decisions file is absent or unreadable, and `401` for a request with no bearer token; the existing probe/403 authentication path is unchanged.
- PC-10: The pull reads body and age from one response; a hub response with no integer `age_seconds` is treated as an unreachable source (held file aged), never as fresh.
- PC-7: No key, token or source body is printed or logged; stderr carries the reason only.

## Risks and rollback

- Hub and pull deploy out of step: an old hub gives no age, so the pull reports stale (safe, visible). A new hub with an old pull ignores the extra field only if the old pull tolerates unknown keys; both directions are covered by S26.
- The hub's decisions file is not touched when no daemon-side publisher runs in the cloud: the age then grows and the panel goes stale, which is the true state (see open question 5).
- A source with no age support: the pull then reports stale (PC-2) rather than guess; the runbook must give the command. Risk accepted: a false stale is visible and cheap, a false fresh is the bug.
- The source's clock is wrong: an age is a duration, so the skew cannot make a stopped daemon look young beyond the pass interval.
- Rollback: revert the pull PR and, separately, the hub PR (then roll the hub image back); the hub's extra field and 503 are the only visible change; `decisions_pull.py` returns to the merged 3d885d7 behaviour (the plugin and the daemon are untouched, so nothing else moves). A held file written by the new pull is the same shape, so the old pull reads it.

## Open questions

1. (Settled in v2) The age reaches the pull in the same response as the body (`age_seconds` from the hub); `--age-command` stays for a plain-file source only.
2. Is the 60 s future tolerance right? Planned: 60 s; adjust only with a reason.
3. Is 2**31 - 1 the right generation bound? Planned: yes (a pass every second reaches it in about 68 years).
4. Does the runbook (Cloud way back, #1079) need a line for the age command? Planned: a follow-up, not in scope here.
5. Who writes or touches the hub's copy of decisions.json? The hub only serves a file at `decisions_path`; something must refresh its mtime. Proposed answer: the daemon-side publisher in the cloud touches it every pass, exactly as `publish` does with the local file (an `os.utime` on an unchanged list, an atomic rewrite on a change), on the volume the hub reads; the hub itself never writes it. Owner: the owner of the hub deployment (#1148) to confirm; until confirmed the age is only as live as that publisher.
6. Does the hub clock or the file's mtime granularity (whole seconds) need a tolerance? Planned: no; the 180 s limit is far above a second.
