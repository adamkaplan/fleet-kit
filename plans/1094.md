### Cause (stated first, from the code)
This is a tightening-only follow-up of the merged `charter set` guard. In `cmd_charter` (`bin/fleet-switchboard`, the `pre` block near line 27357 and `guard` near line 27375) the reads are `engine.intents.parent(value, repo0)` and, only for a root issue, `engine.intents.issue(value, repo0).labels`. Both go through `IntentReader._cached` (near line 19328, `parent` near 19362, `issue` near 19347), a ttl cache keyed by `(kind, repo, number)`; the label read is therefore a cached read, not a fresh one. The batch readers found that 3 of 12 mutants of that guard survive: the rig's fakes ignore the `repo` argument, so a build that reads the wrong repository (or caches across repositories) still passes. The panel kind needs the same two reads (a pull request is known from the item; an issue's plan state comes from data already held, or one bounded cached read per issue through the same `_cached`), so the kind work reuses that path and must not add a read per refresh. The panel plugin is `plugins/fleet-decisions-tui` (`decisions.mjs`, `tui.tsx`); the daemon only supplies the kind. The "plan comment" reading is the one the plan checks use (the latest comment headed `Plan (scenarios)`).

### Approach (what, not how)
The daemon supplies a kind per item: pull request, issue with a plan, issue without one, or unknown. The plugin maps the kind to one emoji from a single table of three symbols plus a neutral marker, and prefixes each row. An unreadable kind shows the neutral marker, never a guess. Plan state is read once per issue and cached (or taken from held data), so a refresh adds no read beyond the panel's own. The rig's fakes for the guard tests are made to honour the `repo` argument so the three surviving mutants fail. One docs line gives the legend.
