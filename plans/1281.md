### Cause (stated first, from the code)
This is a tightening-only follow-up of the merged CI read (#1237, PR #1244; read on the #1237 branch head). Four Lows remain.
1. `read_check_runs` (`bin/ci_runs.py`, about line 246) returns the runs as whole when `len(runs) >= total` or when a short page arrives with a non-int total. It never refuses a total BELOW the runs read: a full first page of 100 runs with `total_count` 50 hits `if isinstance(total, int) and len(runs) >= total: return runs, None`, so it was accepted (probed). GitHub's own count contradicts the read, so the head must not be read as complete.
2. `validate_plan_gates` (`bin/plan_ledger.py`, the `ci_workflows` branch, about line 950) raises "must be a list of at most 20 workflow names", while `missing_workflows` takes a workflow id or a `.github/workflows/<file>` path and never the display name. The text names what the code does not check.
3. `latest_runs` (`bin/ci_runs.py`, about lines 167 to 194) keeps, per workflow identity, `top[ident] = max(top.get(ident, (run, 0)), (run, _attempt(entry)))`: the highest run id, then the attempt. A stale run with a high id beats a newer run by `created_at`; `run_attempt` is read only from the details url.
4. The "Readers of check runs" table in `docs/switchboard.md` (about line 2287) says nothing about how status contexts are grouped (by their context name, no workflow).
The batch readers found no other defect here; this plan changes nothing else.

### Approach (what, not how)
A first page that is full while the reported total is below the runs read is refused with the existing cap refusal, never read as whole. The error text names "workflow ids or paths". "Latest" run of a workflow orders by `created_at`, then `run_attempt`, then the highest run id. The readers table states that status contexts are grouped by name. Nothing else moves.
