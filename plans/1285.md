### Cause (clause 1, stated first)
Arming: `cmd_remind` (`bin/switchboard/reminders.py`, about line 416) parses the time and calls `add_reminder` (about line 73), which always appends a new item (`write_reminders(state_dir, read_reminders(state_dir) + [item])`) with a fresh `uuid` id. Nothing looks for an earlier item with the same owner and purpose, so each arming stays pending (`remind_manage`, about line 382, lists and cancels by id only). Firing: `ReminderFacts.due()` and `__call__` (about lines 119 and 214) turn every due item into a delivery fact, and `prune_delivered_reminders` (about line 235) forgets an item only once its key `reminder:<id>` is in the recipient's transcript or inbox. So two items armed for the same purpose both fire and both queue, and a lane gets the stale copy behind the newer one. Text: the delivered message is cut at `MESSAGE_CAP = 4000` (`bin/fleet-switchboard` about line 3282; `compose` about line 3576; the `[cut at 4000 characters]` marker is added at delivery, about line 4860). `cmd_remind` and `add_reminder` never compare the text with the cap, so the cut is a surprise. No delivery path states how late it is: `due` knows `at` and the pass knows `now`, but the text carries neither.

### Related tightening (a follow-up of the merged charter set guard)
The merged `charter set` guard (`cmd_charter`, `bin/fleet-switchboard` about line 26173: the `pre` block reading `engine.intents.parent(value, repo0)` and `engine.intents.issue(value, repo0).labels`, then `guard` about line 26220) is correct in shape. The batch readers found that 3 of its 12 mutants survive: the rig's fake GitHub ignores the `repo` argument, so a mutant that reads the wrong repository still passes; and the label read goes through the ttl cache (`IntentReader._cached`, about line 18845, used by `issue` and `parent`), so a label changed a moment ago can be judged from a copy. This ask must not loosen that guard. The new reminder tests use fakes that honour the repo argument, and the plan asks for the tightening below only as checks (S9, S10), with no change to the guard's rules.

### Approach (what, not how)
An optional key names the purpose. Arming with a key removes any pending item of the same owner and key, then stores the new one, under the reminders lock so two armings cannot both survive. A fired, undelivered item is dropped at delivery when a newer item with the same owner and key exists, and one audit line names the dropped and the kept id. A delivery that is 5 minutes or more after its due time carries "late by N min" in its text. Arming a text over 4000 characters prints one warning line with the limit and the excess. No key means the old path, byte for byte. The key is part of the match with the owner (the recipient's sender), never the recipient alone.
