### Cause (stated first, from the code)
This is a tightening-only follow-up of the merged change to `charter set`. The batch readers of that change found that 3 of 12 mutants survive its tests. The first cause: the rig's fakes ignore the `repo` argument. In `cmd_charter` (`bin/fleet-switchboard`, the read block at lines 26209 to 26212) the guard reads `engine.intents.parent(value, repo0)` and then `engine.intents.issue(value, repo0).labels`; a fake that answers for any repo lets a build that passes the wrong repo (or none) stay green. The second cause: the label read goes through the ttl cache, `IntentReader._cached` (line 18845), keyed `("issue", repo, number)`; `IntentReader.parent(` (about line 18885) uses the same cache under `("parent", repo, number)`, so a stale label or parent can be served inside the ttl and the tests never age or invalidate it. The guard that judges the result is in `guard` (about lines 26230 to 26235: `pre["parent"] is not None` refuses as an ask, `not pre["labelled"]` refuses as not a charter). This slice's own launch work is the part of the ask for the scratch directory, and it is built so that its tests do not repeat these two gaps: its fakes check the path they are given, and no read of the directory goes through a cache.

### Approach (what, not how)
`launch` makes one scratch directory per agent under the user's own state area with the one private-directory helper (private mode, owned by the user, never through a symlink) and refuses to launch when the path is unsafe. Its path is exported as `FLEET_SCRATCH` in every launch kind with a local side and named in the brief. A launch of an agent that already has it reuses it and never empties it. The tests use fakes that record and check the path argument (so a wrong path fails), and the tests of the `charter set` guard get the same strictness: the fakes answer only for the repo asked, and the cache is aged or invalidated between reads. No clean-up is changed.
