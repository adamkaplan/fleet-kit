## Cause (found first, from the recorded case)

Recorded case: the owner declined to approve a change only because it touched a path on the matrix, with no reason given why the decision was his. Reading main:

- `bin/impact_floor.py`, `owner_decide(...)`: every hold reason is built as a bare string: `"top tier path (%s): %s"` (class name and paths), `"clear_code_paths (the clear and hold machinery, never delegated): ..."`, `"top tier path (permissions): ..."`, `"rating: ... class %s"`. They say the matched path and rule, never why the matter is the owner's. `top_tier_hits`, `owner_hold_rule`, `clear_code_paths`, `narrow_paths` read `docs/review-laws/impact-matrix.json` `owner_hold` (`top_tier_classes` credentials, identity, authority; `top_tier_paths`; `top_tier_outside_floor`; `narrow_by_diff`; `delegated_clear.clear_code_paths`). That block has NO rationale field and NO "who may decide" field: every class is owner-only by construction. `owner_decide` returns only "hold", "second-review" or "none".
- `bin/fleet-switchboard`, `pr_floor_report`: carries `owner_decision` and `owner_reasons` (those strings) plus `top_tier_hits`; `cmd_impact_floor` prints them ("impact floor for ...", "because: ..."). The matrix has no check command today: `cmd_impact_matrix` only prints, and `owner_hold_rule` fails closed (None means every change holds) without reporting which rule is wrong.
- `bin/impact_hold.py`, `_apply_impact_hold_locked`: applies the labels (`merge-captain`, `hold-impact`) and the audit line from `report`; the reason shown is that same string. The owner's Decisions list reads the same decisions (the `captain` rows, `d["holds"]`, `review_evidence`/`headline`, see the function that lists the owner's holds near `chat_clear_pass`), so the Decisions row repeats the path and rule only.
- `bin/fleet-switchboard`, `_held_defects` (used by `pr-explain --check` and gate G6b, registered in `bin/plan_ledger.py`): requires `## Why this needs you` (one to three sentences, no placeholder), a Before/After table, an Example, Questions. It checks form only; no rule says that sentence must give the owner's reason.
- `bin/delegated_clear.py` (`who_can_clear`, `refusal_items`, the score rule) already records a Chief of Staff clear by score or by name; the "clear by score or by name with grounds in the reason" of clause 3 reuses it (`impact_clear_core`, `reason_problems`).

Re-verified against main: none of the new parts exists (no rationale list, no decider field, no advisory decision, no matrix check, no rationale rule in `_held_defects`). Existing pieces to reuse: the Chief of Staff clear, `narrow_by_diff` (a prior content-based narrowing), `second-review` as a softer decision.

## Constraints

- PC-1: Nothing is relaxed by default. The shipped matrix marks EVERY class and rule owner-only; the new field's absence, a malformed value or an unknown value reads as owner-only (fail closed, as `owner_hold_rule` does). Reason: the owner approves each hand-over.
- PC-2: Never handed over, whatever the matrix says: `clear_code_paths` (the clear and hold machinery), the credentials class, issuance (`cloud/launcher/token_mint.py`, `app_token.py`), the merge shim and `shims/**`, `bin/merge_gate.py`, `docs/review-laws/impact-matrix.json` itself. A matrix that marks one of them for the Chief of Staff is a matrix error reported by the check and read as owner-only by the floor.
- PC-3: The stricter class wins: one owner-only path in a pull request holds it, even beside advisory-class paths; unreadable or incomplete file lists, ratings and class "missing/unknown" stay holds.
- PC-4: An advisory hold writes NO hold label and does not stop the merge gate by itself; it is shown as advice naming the grounds to check (independent reads recorded at the head, a green run, no widening). The Chief of Staff's decision is recorded through the existing clear by score or by name, with the grounds in the reason, so the audit shows it.
- PC-5: The rationale list is fixed and kept in the matrix (six entries as in the ask); a rule or class names exactly one entry; the code has no rationale text of its own (as it has no path list of its own).
- PC-6: Public-safe names in docs, examples and test fixtures.

## Out of scope

- Handing any class over: this change ships the mechanism with every class owner-only; the owner decides each hand-over afterwards, by his own PR to the matrix.
- Changing the impact rating cells, the second-review rule or `narrow_by_diff`.
- Changing who may clear a hold, or the delegated-clear score rule.
- No workflow files, no issue writes.

## Areas touched

- `docs/review-laws/impact-matrix.json` (HELD: listed as a force and top tier path): new rationale list, per-rule rationale, per-class decider.
- `bin/impact_floor.py` (HELD: authority class, in `clear_code_paths`): `owner_hold_rule` reader, `owner_decide` (new "advisory" value, rationale, stricter wins), a new matrix check function.

## Risks and rollback

- The new "advisory" value could leak into label or merge code as an unknown decision. Mitigation: S6, S20 and the mutants; every reader falls back to hold on an unknown value.
- A matrix error silently relaxing a hold: the floor reads every unknown or malformed decider as owner-only (S11, U2), and the check reports it.
- Rationale text drift between the matrix, the floor output and the docs: one source (the matrix); S18 compares.
- Rollback: revert the PR; with no class handed over, no hold changed, so behaviour returns to today's.

## Open questions

1. Rationale granularity: one per class, or per rule? Proposed: per class with an optional per-rule override, so a single-path rule can say "cannot be undone".
2. Where the advisory is shown: Decisions list as a Chief of Staff row or a notice? Proposed: a Chief of Staff row, never an owner row.
3. Which classes the owner hands over first (agents without permission change, docs, tests)? Not decided here.
4. Should "a named other risk" require a free-text name? Proposed yes, one short sentence, checked non-empty by the matrix check.
