### Cause (clause 1, stated first)
Where `send` refuses. `_cmd_send` (`bin/fleet-switchboard`, about line 13651) calls `engine.send(...)` (about line 3277). Its docstring says "Stores nothing". It builds ONE `Fact` of kind `send` and calls `send_fact` (about line 3315), which calls `self.plan(...)`. `_plan_pending` calls `decide` (`bin/switchboard/decision.py`, `hold_reason` at line 27, the hold branch at about line 70). When the plan's action is `hold`, `send_fact` writes one audit line `hold`, calls `note_held_send` (about line 10414: it keeps only the sender name and the time, so a long block can be reported; it keeps NO text) and returns `{"sent": False, "action": "hold", ...}`. `_cmd_send` then prints `not sent to <name>: hold (<reason>)` and exits `EXIT_HELD` (3, line 346: "nothing was sent"). The text lives only in that one process: no queue, no file. The sender must send it again, and a sender that did not read the exit status never knows. Endpoint (cloud) agents have the same refusal in `_send_by_registry` through `es.blocked_reason(..., hold_reason)`.

How the held state is set and cleared. There is NO stored hold flag. `hold_reason(observation)` is a pure function of the agent's latest observation, read again on each call: it answers a reason when the agent is claimed by two sessions (`conflict`), has a `problem`, has status `blocked` (herdr shows "blocked on a permission request or a question"), or a status other than `idle` or `working`; for an agent that is not found (gone) the reason is `<name> not found: ...` (`discovery.missing`). A turn that ended on a provider error leaves the pane showing `blocked`, so the pane is on hold with nothing open to answer, which is the recorded case of 27 Oct. The hold clears by itself when herdr's status for that pane next reads `idle` or `working` (an answer, a `resume`, a new prompt). Nothing queues in between; the `blocked_tick` report (line 10470) counts held sends only by sender and time and says so at 20 minutes.

What the #1337 safety net (PR #1346, commit 7cf9170f; the implementer must confirm which branch carries it, it is not in `main` at c7dcab0c) covers. `undelivered_wake_tick` reads, at the end of each pass, every agent whose status is `idle` and for which `hold_reason` is None; it takes the daemon's own queued wakes from the v2 inbox (`queued_wakes`), keeps those absent from the transcript and older than `undelivered_wake_minutes` (15), and resumes the agent once per incident through `resume_ended_turn` (a 10 minute rate record, refusals for an open permission request or question or a working session), with one audit line `undelivered.resume`; one notice to the Chief of Staff follows if still absent. COVERED: an idle agent whose queued wakes were admitted and never started a turn (the daemon's wakes, reminders, held-PR notes) gets one bounded resume, and that holds whatever the cause of the idle. NOT COVERED: (a) a message refused at a hold is never admitted, so no queued wake exists for the rule to find; (b) the rule skips an agent that is `blocked`, which is exactly the pane on hold; (c) it does not look at the last turn's error: it is keyed on an undelivered queued item older than 15 minutes, not on a provider error (the separate `resume_first_recovery` reads the error, only inside the blocked report, only for 499, ECONNRESET or a timeout, only for a stop with nothing open); (d) a queued item younger than 15 minutes waits; (e) a test that shows the case "idle after a provider error, with queued messages, gets one bounded resume" does not exist yet.

### Approach (what, not how)
A message to a pane whose `hold_reason` is a hold (blocked, other status, or a `problem`) is kept in that recipient's own queue (a per-recipient file in the state directory, written atomically, under a lock, bounded in count and size, 0600), with its sender, its sent time, its issue and its text, and the sender sees "queued (the pane is on hold)" and exit status 0. A recipient that is gone (not found) or retired, a name in a `conflict`, and a message over the size cap still refuse with their reason and queue nothing. When the observation next shows `idle` or `working` the daemon delivers the queue in sent-time order (ties by a sequence number), each message once (the key is recorded as delivered, as the dedupe already does), through the ordinary delivery path. A message sent more than 24 hours earlier is delivered marked with its sent time. The #1337 recovery is shown, by a test, to resume once an agent that is idle after a provider-error turn with queued messages; the case is named in `docs/switchboard.md` beside "An undelivered wake is recovered". The #1337 rule is changed only if the test shows the case is not covered, and then by the smallest addition.
