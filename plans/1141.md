### Cause (clause 1, stated first)
The daemon already reads the pull request's check state for each open pull request and the default branch's latest run in its pass, but nothing turns a FAILURE at a head into a message: the recorded case (a required check failed at an open head, about eight hours unseen, no message to the lane's orchestrator) has no notice that carries it. The existing notices to an orchestrator (the ask and comment wake path and the delivery rule's held-while-blocked path) can carry a check failure and a red default branch unchanged.
The merged change this follows is the `charter set` guard in `cmd_charter` (`bin/fleet-switchboard`, the `pre` block: `engine.intents.parent(value, repo0)` about line 27358 and the label read `engine.intents.issue(value, repo0).labels` about line 27361, with the refusals in `guard` just after). The batch readers of that change found that 3 of 12 mutants survive: the rig's fakes ignore the repo argument, so a build that reads the parent or the label for the wrong repository still passes. Also the label read goes through `IntentReader._cached` (about line 19328, the `("issue", repo, number)` key, answered from a ttl cache), so a stale label can be judged; `IntentReader.parent` (about line 19362) is cached the same way under `("parent", repo, number)`. This follow-up tightens only that: the fakes must honour the repo argument, and the label read must not be answered from a stale entry. The same discipline binds the new notices: a per-repository read, keyed by repo, head and check, never a shared cached answer across heads.

### Approach (what, not how)
On the existing pass, a required check that concluded FAILURE at the head of an open pull request owned by a lane's worker sends the lane's orchestrator one message (pull request, check, run link, head), remembered per head and check. A red default branch run or merge queue sends one alarm per change to the repository's lane orchestrators and the Chief of Staff, and one message when it turns green. Cancelled, skipped, neutral, running, and non-required checks send nothing. All go through the delivery rule (held with the reason while blocked), never typed into a pane. No new platform read; the first pass after a start reads these before the rest (#1140 cold start). The tests' fakes honour the repo argument so the three surviving `charter set` mutants die, and the label read is fresh at the guard.

### Done when (copied exactly from the ask)
Done when: (1) the cause is found and stated first, from the recorded case (a required check concluded failure at the head of an open pull request and about eight hours passed before anyone saw it; no message told the lane's orchestrator): what the daemon already reads about checks (the pull request's check state, the default branch's latest run) and which of the existing notices could carry it; (2) when a required check concludes FAILURE at the head of an open pull request that a worker of the lane owns, the lane's orchestrator gets ONE message naming the pull request, the check, the run link and the head, once per head and check (a new head or a re-run that fails again is a new event); (3) when the default branch's latest completed run, or the merge queue, turns red, the lane orchestrators of the repository and the Chief of Staff get ONE alarm per change (the run, the head, the failing job), and ONE message when it turns green again; (4) a check that is cancelled, skipped, neutral or still running sends nothing; a failure of a check that is not required sends nothing; (5) the messages go through the delivery rule (held while the receiver is blocked, with the reason), never typed into a pane; (6) no extra read of the platform beyond the check state the pass already reads for open pull requests and the default branch's latest run, and the daemon's cold start (#1140) is stated: after a start the first pass reads these before the rest; (7) tests: a failure at a head (one message), the same head again (none), a new head failing (one), a cancelled check (none), a red default branch (one alarm to the right receivers), back to green (one message), and a mutant that repeats the message, one that alarms on a cancelled run and one that skips the green notice fail; (8) the documentation names the two messages and their receivers.
