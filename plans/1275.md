### Cause (clause 1, stated first)
The wake path has no memory of what it already said. `add_reminder` is called from `tell` (`bin/fleet-switchboard`, about line 14837) with the text `"Blocked agent: " + text` on every pass that still sees the agent blocked, once per recipient, and nothing compares it with the last reminder of the same kind and subject. `Delivery._undelivered` (about line 4784) drops a fact only when its key is already in the recipient's session; a reminder re-keyed on each pass is never "delivered" in that sense, so it re-fires. Sweeps (S5), load alerts (`alert_wake_pass`, about line 14279) and triage lists are each composed and sent as their own message, and `compose` (about line 3576) orders what it carries without regard to age, so a newer result can sit behind older reminders and arrives hours late. No step asks whether the Chief of Staff already answered that issue since the finding. The recorded case: a session with a five-page backlog of repeated reminders, and work that looks stuck.

Related tightening of the merged `charter set` guard (parent #587, read in `cmd_charter`, about lines 26200 to 26237): the batch readers found that 3 of 12 mutants survive, because the test rig's fakes ignore the `repo` argument of `engine.intents.parent(value, repo0)` and `engine.intents.issue(value, repo0)`, and because the label read goes through the ttl cache `IntentReader._cached` (about line 18845), so a stale label is accepted. The fakes must honour the repo, and the guard must not use a stale label.

### Approach (what, not how)
- Repeat rule: a reminder with the same kind, same subject and unchanged state is delivered at most once per 6 hours; a change of state delivers at once.
- One message per wake: sweeps, triage and load alerts of one wake are one message, one line per item.
- Answered items: an item the Chief of Staff answered (a send on that issue since the finding) is not re-raised until its state changes.
- Order: deliveries go oldest-last, that is newest first; a newer result is never held behind older reminders. Ties keep the order of the findings.
- Never suppressed: an owner wait, a held PR, the FIRST report of a dead or blocked agent. Only repeats.
- Tests: a table lists every finding class; a completeness test derives from the table and fails if a class is dropped from the merged message. Mutants of the rule and of the `charter set` guard each fail a test, and the rig's fakes honour the repo argument. The label read for the guard is made fresh (bypassing the ttl).
- Docs state the 6-hour rule, the one-message rule, the answered rule and the order.

### Done when (copied exactly from the ask)
Done when: (1) the cause is stated first from the recorded case (repeating S5 sweeps, "Blocked agent" reminders, load alerts and triage lists re-fire for items already answered, and deliveries arrive hours late behind newer results); (2) a repeated reminder for the same item (same kind, same subject, no change in its state) is delivered at most once per 6 hours, and sooner only when the state changes; (3) sweeps, triage and load alerts of one wake are one message (one line per item), not one message each; (4) an item the Chief of Staff already answered (a send on that issue since the finding) is not re-raised until its state changes; (5) deliveries to the Chief of Staff go oldest-last: a newer result is not held behind older reminders (state the order); (6) tests with mutants, no finding class dropped (a table-derived completeness test), the docs say it. It must not hide an owner wait, a held PR or a dead/blocked agent's FIRST report: only repeats.
