### Cause (clause 1, stated first)
`send` takes its text only from the command line. In `_cmd_send` (`bin/fleet-switchboard`, about line 13700) the text is `text = " ".join(args.text).strip()`, with `nothing to send` as the only check; the same line is in `_send_by_registry` (about line 13660, the endpoint route) and in the cloud path (`cmd_send` via `run_cloud`). There is no file option. The cap is `MESSAGE_CAP = 4000` (line 1848) and applies at delivery, not at the command: `engine.send(...)` queues a `send` fact and `compose(...)` (about line 2960, the delivery code) cuts a message past the cap with `[cut at 4000 characters]`. The guard after it raises `MessageTooLong` ("message is N characters and would be cut ... Write it to a file in the opencode temp dir and send the path") which `_cmd_send` prints and exits `EXIT_USAGE`: a refusal with no `--file` hint, and the check only sees the length once the header and ask sections are added; a long text is never carried whole.
`remind` is different. #1355 (PR #1393, branch `origin/c1355`) adds `--text-file F` to `cmd_remind` with `read_text_file(path)` (regular file only via `fstat`, UTF-8, no NUL, not empty, at most `TEXT_FILE_MAX`), refuses command-line text over `TEXT_CAP` with the hint "use --text-file F", and delivers a long reminder in parts. That sits on #1315's `finding_parts(fact, budget)` and `compose(...)` with `resume` in branch `origin/c1302`, which split whole lines into chunks and never cut.
Check stated as clause 1 asks: #1355's part form does NOT cover `send`. It is wired into `cmd_remind` and `add_reminder` only; `cmd_send`, `_cmd_send` and `_send_by_registry` have no `--file` and no part path. (`read_text_file` also does not refuse a symlink; this ask's rule does.)
Dependency: this ask builds AFTER #1315 (c1302) and #1355 (c1355) land. It reuses what they add and does not copy it.

### Approach (what, not how)
- `send <name> --file <path>` reads the text through ONE shared function, `read_text_file` (from #1355), extended with the rules: a regular file, not a symlink that leaves the user's directories, at most 100 KB; `remind --text-file` then uses the same function, so the two cannot drift. Text from words and `--file` together is refused.
- The split into parts is ONE shared function used by both `remind` and `send`: `finding_parts(fact, budget)` of #1315 (whole lines, a long line split with a continuation mark, never cut), reused as it is, or hoisted to a neutral name `text_parts(text, budget)` with `finding_parts` calling it. No second splitter.
- A text within the cap is one part with NO header. A longer one is delivered as numbered parts, each under the cap, in order, each starting with a header such as "part 2 of 3". The sender is told on stderr how many parts were queued. If one part fails, the failure names that part and no later part is sent.
- Command-line text over the cap with no `--file` is refused at the command, before anything is queued, with the reason (characters, cap) and the hint "use --file F". This also replaces the late `MessageTooLong` path for a plain send.
- The same on the endpoint route (`_send_by_registry`) and the cloud route, which take the text the same way.
