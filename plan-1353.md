## Cause (clause 1)

Measurement pods of a product repository spend about 20 of their 60 minutes compiling PostgreSQL 16 and two extensions (vector, message queue) from source on every run. Building once in the image removes that cost from every pod.

## Open choices (one recommendation each, with the cost)

- (a) Build stage. Recommendation: a separate build stage with compilers; copy only the installed files into the final image. Cost: image grows by the installed server and extensions only (tens of MB, measured), no compilers in the final image; build time grows once, in the operator job.
- (b) Source. Recommendation: the PostgreSQL project's release tarball with a pinned sha256, plus a pinned source archive and sha256 for each extension, each checked by sha256sum -c before unpacking (the Node and agent pattern). Versus apt packages: the version moves with the distribution and the extensions may be absent or at another version, so the pin is weaker. Cost: a bump edits version and checksum ARGs.
- (c) Data directory. Recommendation: a scratch path the worker owns on the scratch volume, created by the lane, never at pod start. Cost: data is lost with the pod, which is wanted.
- (d) Start. Recommendation: a documented one-line command run by the lane as the worker user (initdb then pg_ctl start on a local socket); no entrypoint change. Cost: each lane runs one line.
- (e) Size and start time. Measured by the operator from a real build, before and after, and recorded in the PR (live scenario).

## Out of scope

Entrypoint changes, network policy, guard and permission files, the arm64 build, any product repository change.

## Constraints

- PC-1: the pinned tests (test_dockerfile_node.py, test_dockerfile_agent.py) are not changed; a pin changes only by the ask whose approved plan names it, and this plan names none (shared contract of the image build).
- PC-2: security floor: no download without a pinned checksum, verified before unpacking.

## Risks and rollback

Rollback: re-point workers at the previous image digest, kept in the registry until the new image has run live. Nothing is half-applied: the change is one image.
